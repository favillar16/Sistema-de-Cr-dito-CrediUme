**Connection health: gRPC keepalive is configured on BOTH sides and the two must stay in sync (added 2026-08-18).** The reported symptom was that the LAN link between a client PC and the server dropped during a session. Root cause: neither side set any channel options, so the five channels the client opens at startup and holds for the whole 8-hour session sat idle for long stretches, and the Wi-Fi router's NAT table (plus Windows' Wi-Fi power management) silently discarded the idle TCP flow. Neither end noticed — the socket stayed "open" for both — so the operator only discovered the break when a click hung on TCP retransmission timeouts. HTTP/2 PING fixes both halves at once: it keeps the router's NAT entry alive, and it gives gRPC its own liveness signal, so a dead link is detected in ~40 s and the channel reconnects **in the background**, before the user's next click.
- **The two sides are one setting, not two.** `cas_client/config.py`'s `GRPC_KEEPALIVE_TIME_MS` (30 s) must be **≥** `cas_server/config.py`'s `GRPC_MIN_PING_INTERVAL_WITHOUT_DATA_MS` (10 s). gRPC's server default for that is **300000 ms (5 min)**, so a client pinging every 30 s against an unconfigured server gets `GOAWAY / ENHANCE_YOUR_CALM / too_many_pings` and is **deliberately disconnected** — i.e. "fixing" only the client side makes the reported problem strictly worse. This was verified empirically, not assumed: an intentionally aggressive 1 s-ping client does earn that GOAWAY against our server. `tests/client/test_connection_keepalive.py` pins the relationship.
- `grpc.keepalive_permit_without_calls=1` is the option that makes the rest useful — the link dies precisely when no RPC is in flight, so a keepalive that only ran during calls would prevent nothing.
- **Every RPC now goes through `grpc_client._invoke()`**, which replaced ~31 verbatim-duplicated `try/except grpc.RpcError` blocks. It owns the connection policy in one place: a **per-call timeout** (`GRPC_CALL_TIMEOUT_SECONDS`, 20 s — without it an unreachable server hung `AsyncWorker` forever with the progress bar spinning and no way to cancel) and **`wait_for_ready=True`**, so a call landing inside the automatic reconnect window waits instead of failing with a spurious `UNAVAILABLE`. `wait_for_ready` delays sending; it never re-sends, so it is exactly as safe for `RecordPayment` as for a read.
- **`DEADLINE_EXCEEDED` is handled in `AsyncWorker`, not per view** — same choke-point argument as session expiry, and it only became reachable once calls got a deadline, so no view's `_friendly_message()` contemplated it (all would have said "Ocurrió un error inesperado" to an operator with a network problem). `session.CONNECTION_LOST_MESSAGE` deliberately states that *the operation was not recorded* — a cashier whose payment fails needs to know whether re-charging would double-post. `LoginView` is excluded as always (its own `_LoginWorker`) and got the same branch added by hand.
- **`cas_client/connection_status.py` + a "● Conectado / ● Sin conexión" pill in `HeaderBar`.** The operator previously had no way to know the link was down until an action failed — which for a teller means finding out *after* taking the customer's cash. It subscribes to the channel's own connectivity state (`Channel.subscribe`), the same state the pings feed; it does **not** poll (that would be redundant traffic that could also contradict the channel). `IDLE` counts as connected on purpose — a channel that went idle from disuse is healthy and connects on the next call; treating it as down would false-alarm every quiet moment. Only the Auth channel is watched: all five point at the same host, so five subscriptions would report the same news five times, and Auth is the only one that exists before login.

**Session-expiry handling (added 2026-08-15, during a pre-delivery client-side review).** `BR-AUTH-003`'s JWT lasts 8 hours with no refresh, so a client left open across a workday reliably outlives its own token — and until this session every view except `LoginView` fell through to its generic `"Ocurrió un error inesperado. Intente nuevamente."` on the resulting `UNAUTHENTICATED`, with no way back to the login screen short of killing the app. The fix lives in **one** place: `AsyncWorker.run()` (`cas_client/widgets/async_worker.py`) now checks `_is_expired_session(exc)` *before* delegating to the per-view `error_translator`, emits `session.session_events.expired`, and reports `session.SESSION_EXPIRED_MESSAGE`. `AsyncWorker` is the single choke point every authenticated gRPC call in the client already passes through, so this covers all ~25 call sites at once instead of hand-editing five `_friendly_message()` functions that would then drift. **`LoginView` is deliberately excluded** — it uses its own `_LoginWorker`, and `UNAUTHENTICATED` there means wrong password / locked account, not an expired session; `tests/client/test_session_expiry.py` pins that distinction (along with the equally important one that `UNAVAILABLE` must *not* be treated as expiry, or a briefly-down server would eject the operator and discard whatever form they were filling). `cas_client/session.py` gained a module-level `_SessionEvents` QObject singleton for the signal — emitted from the worker thread, but since the object lives on the main thread Qt delivers it queued, so `MainWindow._on_session_expired()` runs on the UI thread where swapping the stacked widget is safe. That slot clears the `Session`, returns to `LoginView` and calls its new `notify_session_expired()` (8-second toast, clears the password but keeps the username); it deliberately does **not** call `Logout`, since the token the server just rejected is the only one it could send, and it guards on `access_token` being non-None so several simultaneously-failing in-flight calls tear the session down only once.

```bash
pip install -r requirements.txt
```

Regenerate gRPC stubs after editing any `protos/*.proto` file (writes into both `cas_server/` and `cas_client/`):
```bash
python scripts/generate_protos.py
```

Run the server **in development** (binds `GRPC_HOST:GRPC_PORT` from `cas_server/.env`; TLS is active whenever `GRPC_TLS_CERT_FILE`/`GRPC_TLS_KEY_FILE` are set, which they are on the deployment machine — the "TLS is deferred" note that used to sit here is obsolete):
```bash
python -m cas_server.server
```

**On the deployment machine, do not run that command.** `cas_server` is a Windows service there (`CASServer`, see "Deployment model" below); a second process would lose the race for port 50051 and die. Operate it from an elevated PowerShell instead:
```powershell
Get-Service CASServer
Stop-Service CASServer
Start-Service CASServer
```

Run the client:
```bash
python -m cas_client.main
```

Create the first ADMIN user (needed before any login is possible):
```bash
python -m cas_server.scripts.seed_admin <username> <password>
```

Database migrations (config at `cas_server/alembic.ini`, scripts in `cas_server/migrations/`). **Run from inside `cas_server/`, not the repo root** — `alembic.ini`'s `script_location = migrations` is a relative path that Alembic resolves against the current working directory, not the ini file's location, so `alembic -c cas_server/alembic.ini ...` run from the repo root fails with `Path doesn't exist: '<repo root>/migrations'` even though that's the invocation pattern you'd expect to work:
```bash
cd cas_server
alembic upgrade head
alembic revision --autogenerate -m "message"
cd ..
```

## Architecture

Client-server system over gRPC (see `docs/ES-000_Engineering_Specification.md`):

- **`cas_client/`** — PySide6 desktop app. Presentation + client-side input validation only; never touches the DB, always goes through a gRPC stub (`cas_client/grpc_client.py`).
- **`cas_server/`** — business logic, deep validation, persistence. RPCs return standard gRPC status codes (`OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `UNAUTHENTICATED`, `PERMISSION_DENIED`).
- **`protos/`** — source of truth for the client-server contract.
- **PostgreSQL** — system of record, accessed only from `cas_server` via SQLAlchemy.

### Generated stub imports (non-obvious gotcha)

`protoc` is invoked with no `package` option, so the generated `*_pb2.py`/`*_pb2_grpc.py` files import each other with flat statements like `import auth_service_pb2` rather than package-qualified ones. Since these files are generated straight into `cas_server/` and `cas_client/`, each package's `__init__.py` does `sys.path.insert(0, os.path.dirname(__file__))` so those flat imports resolve. Application code follows the same convention — e.g. `cas_server/services/auth_service.py` does `import auth_service_pb2`, not `from cas_server import auth_service_pb2`. Keep new service modules consistent with this pattern rather than "fixing" the imports.

### Request flow (auth vertical slice as the template for new services)

1. `cas_server/server.py` builds a `grpc.server` with a single `AuthInterceptor` (`cas_server/security/interceptor.py`) wired in, then registers `AuthServicer`, `ClientServicer`, `LoanServicer`, and `DashboardServicer`.
2. `AuthInterceptor` runs on every RPC: public methods (`rbac.PUBLIC_METHODS`) pass through; everything else needs a valid `authorization: Bearer <jwt>` metadata entry, the JWT must decode and not be in the `revoked_tokens` table, and the token's role must be in `rbac.allowed_roles(method)`. Unlisted methods are denied by default. On success it stashes `TokenClaims` in a `ContextVar` (`cas_server/security/current_user.py`) for the duration of that call only.
3. New RPCs must be added explicitly to `cas_server/security/rbac.py`'s `PUBLIC_METHODS`/`METHOD_ROLES` — an RPC with no entry there is unreachable (`UNIMPLEMENTED`/deny-by-default), not "open by accident." **`DeleteLoan` (BR-LOAN-012, added 2026-08-18) is a second example of an authorization boundary that is only half in `rbac.py`**: the role gate lives there (`CREDIT_ANALYST_AND_ABOVE` as of 2026-08-19, previously `MANAGER_AND_ABOVE`), but *which loans* may be deleted is a state+payments check inside `loan_service.py` — same "which method vs. which rows" split as `cash_service.py`'s `_es_supervisor()`. `rbac.py` defines named role tiers (`CASHIER_AND_ABOVE`, `CREDIT_ANALYST_AND_ABOVE`, `MANAGER_AND_ABOVE`) that mirror the seniority order implied by the specs — reuse these instead of writing out ad hoc `frozenset({...})`s per method. **This session changed an existing boundary for the first time (`BR-CAJA-005`)**: `CreateClient`/`UpdateClient`/`CreateLoan`/`UpdateLoanProposal`/`UpdateLoanGuarantee`/`UpdateLoanCharges` moved from `CASHIER_AND_ABOVE` to `CREDIT_ANALYST_AND_ABOVE`, because the `CASHIER` role stopped being unassigned and became a real teller who should not originate credit. Six tests in `test_client_interceptor_integration.py`/`test_loan_interceptor_integration.py` that asserted the old boundary were rewritten rather than deleted — if you are tempted to "restore" `CASHIER` on those methods because a test name says `allows_cashier` in git history, read `specs/cash/README`'s BR-CAJA-005 first. Note also that the two role asymmetries in `CashService` (closing someone else's caja, seeing every cashier's arqueos) are **not** in `rbac.py` — they're "which rows", not "which method", so they live in `cash_service.py`'s `_es_supervisor()`.
4. Service methods (`cas_server/services/`) open `SessionLocal()` per call, do their own commits, and write an `AuditLog` row for security-relevant actions (login success/failure, lockout, logout, password reset, client create/update/deactivate/national-id change, loan create/approve/disburse/payment/default/expiry). `client_service.py` and `loan_service.py` share request-parsing/response-shaping helpers from `cas_server/services/common.py` (`analizar_uuid`, `analizar_decimal`, `ip_remota`, `a_marca_tiempo`, `id_actor_actual`) — `auth_service.py` predates that extraction and still defines its own (English-named) equivalents for most of them, so follow `common.py` for any new service rather than the older auth code. **One exception, fixed this session:** `auth_service.py`'s `_commit_or_conflict` used to be a verbatim duplicate of `common.py`'s `confirmar_o_duplicado`; it's now a direct alias (`from cas_server.services.common import confirmar_o_duplicado as _commit_or_conflict`) — English name kept per the language-split convention below, but the logic lives in one place. `confirmar_o_duplicado` itself now only translates an `IntegrityError` to `ALREADY_EXISTS` when the underlying Postgres error is actually a `unique_violation` (`pgcode == "23505"`, `common.UNIQUE_VIOLATION_PGCODE`) — previously any `IntegrityError` (e.g. a NOT NULL or FK failure) was mislabeled as a duplicate; other causes now propagate instead of being masked.
5. `LoansView` (`cas_client/views/loans_view.py`) takes both a `LoanServiceClient` and a `ClientServiceClient` in its constructor — the latter was added so the Documentos feature can fetch client contact details (name/address/phone) when rendering a document, since `LoanService` responses only carry `client_id`. `main_window.py` constructs a single `ClientServiceClient()` and passes the same instance to both `ClientsView` and `LoansView` rather than opening a second channel. On the client, `cas_client/grpc_client.py` wraps stubs and re-raises `grpc.RpcError` as an error object; views translate that into a user-facing message and never show a raw traceback or gRPC code to the user. `AuthClient` (login/logout) raises `AuthError`; `ClientServiceClient`/`LoanServiceClient` raise the more generic `ApiError` (same shape — `.code`/`.message`) since they cover more than authentication. Every client/loan RPC requires a Bearer token, so those two clients take `access_token` as the first arg on every method (`AuthClient.login` is the only public/unauthenticated call). `cas_client/session.py`'s `Session` is a small mutable holder for the post-login token/role/username; `MainWindow` creates one instance and passes it into `ClientsView`/`LoansView` at construction time (before login happens), updating it in place on login/logout so the views always see the current token without being re-created. Long-running calls run on a worker thread via the reusable `cas_client/widgets/async_worker.py`'s `AsyncWorker` (generalizes `login_view.py`'s original bespoke `_LoginWorker` so new RPCs don't need their own `QThread` subclass), driving a `QProgressBar` via signals.
6. Role-gating on the client is UX-only, not authoritative: `cas_client/rbac_ui.py`'s `role_at_least()` mirrors `rbac.py`'s tiers by hand (no shared source between the two processes) to decide which buttons to enable — e.g. "Desembolsar" needs MANAGER+, "Aprobar"/"Marcar incumplido" need CREDIT_ANALYST+, "Cambiar documento" needs ADMIN. The server re-checks everything regardless; keep `rbac_ui.py` in sync with `rbac.py` by hand when adding new gated actions.
   - **User-facing "niveles":** `rbac_ui.py`'s `tier_label()` maps `CASHIER`→"Cajero", `CREDIT_ANALYST`→"Estándar", `MANAGER`→"Agente de Créditos", `ADMIN`→"Administrador" — 4 labels for the backend's 4 roles. **This changed this session:** `CASHIER` used to be folded into "Estándar" because nobody had the role (cash handling had been dropped in favor of transfer/direct debit/account discount, see `transfer_reference` below). The establishment reincorporated a teller, so the role is assigned again and has its own narrower permission set (`BR-CAJA-005`) — showing it as "Estándar" would now misdescribe what that user can do.
   - **The cashier's navigation is a separate list, not a prefix of everyone else's.** `main_window.py`'s `_TELLER_NAV_ITEMS` is `("Caja", "Clientes", "Préstamos")` and `rbac_ui.is_teller()` is `role == "CASHIER"` exactly — deliberately **not** `not role_at_least(role, "CREDIT_ANALYST")`, because the teller is a job, not a rung on the seniority ladder. "Caja" is also shown to MANAGER/ADMIN (they supervise arqueos and can close a caja left open) but not to CREDIT_ANALYST, who doesn't handle cash.
   - **Interest-rate editability (UI-only rule):** `rbac_ui.py`'s `can_edit_interest_rate()` (true for MANAGER+) and `FIXED_INTEREST_RATE` ("0.24") drive the "Nuevo préstamo" form in `loans_view.py`: Estándar users get the rate field pre-filled and read-only, Agente de Créditos/Administrador can type any rate. This is explicitly **not** enforced server-side — `loan_service.py`'s `CreateLoan` still accepts any `interest_rate` from any role allowed to call it (`CASHIER_AND_ABOVE` in `rbac.py`). If this ever needs to be a real security boundary rather than a UX guardrail, that requires a new server-side check (and test) in `loan_service.py`, not just a client tweak.
7. **Language split (non-obvious, server-side only):** `cas_server/services/client_service.py`, `loan_service.py`, `amortization.py`, and `common.py` are written in Spanish end-to-end — local variables, docstrings, comments, `context.abort()` messages, and `AuditLog.action` strings (e.g. `"PRESTAMO_CREADO loan_id=..."`, `"CLIENTE_ACTUALIZADO client_id=..."`). `auth_service.py` (and the rest of the security layer) is still English and untouched. When extending these two services, match the Spanish convention already there; don't mix English identifiers back in. Things that stay in English regardless, because they're fixed by the wire contract or DB schema: proto-generated symbols (`*_pb2*.py`, servicer class/method names like `ClientServicer.CreateClient`, request/response field names like `client_id`/`principal_amount`), and the `LoanStatusEnum` string values returned in `status` fields (`"PENDING"`, `"APPROVED"`, etc.) — translate the sentence around them, not the identifiers themselves. **`cas_client` was not part of this — it keeps the pre-existing convention** (English identifiers, Spanish UI copy only, see "Client UI conventions" below); `clients_view.py`/`loans_view.py`/`grpc_client.py` etc. follow `login_view.py`'s existing style, not the server's.

- `specs/loans/README` — Loan lifecycle (PENDING → APPROVED → ACTIVE → PAID/DEFAULTED/EXPIRED), max 3 active loans/client (`BR-LOAN-001`), 40%-of-income payment cap (`BR-LOAN-002`), 30-day expiry on undisbursed approvals (`BR-LOAN-003`).   - **`BR-LOAN-004` (editable credit proposal, second gap-analysis item after `BR-CLI-006`).** While a loan is `PENDING`, its `principal_amount`, `term_months`, and `first_due_date` are editable via `UpdateLoanProposal`, which re-validates the BR-LOAN-002 40%-of-income cap against the new terms (mirrors `CreateLoan`'s own check) but deliberately does **not** re-check BR-LOAN-001 (PENDING loans never count toward the active-loan cap, per `_ESTADOS_ACTIVOS` in `loan_service.py`).   - **`BR-LOAN-005`/`BR-LOAN-006` (guarantees + charges/informational, third/fourth gap-analysis items — closed out the original 4-item gap analysis).** Rather than a one-to-many child table + dynamic add/remove-row Qt list (no precedent anywhere in this codebase — every existing multi-field group, e.g. `ClientsView`'s reference cards, is fixed-cardinality), both were scoped down to flat nullable columns on `Loan`, same pattern as `first_due_date`/`source_of_funds`: `guarantee_type`/`guarantee_amount` (BR-LOAN-005, one guarantee per loan, both fields must be set together or both blank) and `charge_interest_tax`/`charge_admin_fee`/`charge_cancellation_insurance`/`charge_contracted_insurance` (BR-LOAN-006, each independently optional). Client UI: both live as extra cards on `loans_view.py`'s existing `_PAGE_EDIT_PROPOSAL` page, each with its own independent save button (not chained to the proposal-terms save). `documents.py`'s `liquidacion_html` gained a conditional guarantee/charges breakdown section (`_cargos_y_garantia_block`) — `pagare_html`/`contrato_html` were left untouched. **All 4 items from the original gap analysis are now implemented** (`BR-CLI-006`, `BR-LOAN-004`, `BR-LOAN-005`, `BR-LOAN-006`, `BR-CLI-007`) — see "Recommendations for the next session" below for what's next.
  - **`BR-LOAN-007` (fixed-rate enforcement, now a real server-side rule, not just UX).** `LOAN_FIXED_INTEREST_RATE = Decimal("0.18")` in `config.py` — **changed this session from `0.24`**, because the entity authorised a compensatory interest of **1,5% mensual sobre saldos deudores** and `amortization.py` charges `tasa_anual / 12` per period, so 18% nominal annual is the rate that actually produces 1,5%/month. The old 0.24 produced 2%/month while the Pagaré/Contrato clause was about to promise 1,5% — the documents and the amortization math would have disagreed on a signed instrument. Only affects loans created from now on (each `Loan` stores its own `interest_rate`). Note `rate_percent_mensual()` in `cas_client/formatting.py`: the clauses quote the **monthly** figure derived from the stored annual rate, never a hardcoded "1,5%", so a future rate change can't leave the contract text stating something the schedule doesn't do. `CreateLoan` now rejects a non-standard `interest_rate` when the caller's role is below `MANAGER` (`rbac.MANAGER_AND_ABOVE`), reading the role from `get_current_claims()` — the same mechanism `id_actor_actual` already used for audit logging. **Only fires when `claims is not None`**: direct-servicer unit tests (no `AuthInterceptor` in the call path) always see `claims=None`, so the check is skipped there by design — this mirrors `id_actor_actual`'s existing None-tolerant pattern and keeps every pre-existing `test_loan_service.py` test using arbitrary rates unaffected. The restriction is only actually exercised through `tests/server/test_loan_interceptor_integration.py` (real login → real claims), e.g. `test_create_loan_rejects_non_standard_rate_for_standard_role`/`test_create_loan_allows_manager_to_set_custom_rate`. `UpdateLoanProposal` doesn't touch `interest_rate` at all (per `BR-LOAN-004`), so no second enforcement point was needed. `cas_client/rbac_ui.py`'s `can_edit_interest_rate()`/`FIXED_INTEREST_RATE` doc comments were updated to stop saying "UI-only" — keep the two constants in sync by hand (no shared source between client/server processes, same caveat as `role_at_least`).
  - **`BR-LOAN-008`/`BR-LOAN-009`/`BR-LOAN-010` (installment-level payment tracking, existing functionality documented this session).** `BR-LOAN-008`: `UpdateInstallmentAmount` (`MANAGER_AND_ABOVE`, `ACTIVE`-only) lets an operator fix a specific installment's amount; stored as a row in `LoanInstallmentAdjustment` (one per adjusted installment, `UNIQUE(loan_id, installment_number)`) rather than mutating the computed schedule, applied as an override when `calcular_cronograma` recomputes it. The last installment is never adjustable (it always absorbs the exact remainder). `BR-LOAN-009`: `GetLoanById`'s `payment_status` ("AL_DIA"/"CUOTA_VENCIDA") walks the full schedule FIFO-matched against real payments and looks only at installments already past due — distinct from `remaining_balance`, which is the whole loan's balance regardless of what's overdue. `BR-LOAN-010`: `RecordPayment(installment_number=...)` lets a payment target one specific installment; the server recomputes that installment's exact pending amount itself (same FIFO as BR-LOAN-009) and ignores any client-supplied `amount` for that case, so the amount recorded can't be spoofed. `installment_number=0` keeps the older free-form mode. Client UI: `loans_view.py`'s "Ajustar" button per schedule row (BR-LOAN-008) and the "Cuota a pagar" dropdown next to "Registrar pago" (BR-LOAN-010, populated by fetching `GetAmortizationSchedule` and filtering to unpaid installments). `protos/loan_service.proto` also has `ListActiveLoans` (no request fields, any authenticated role) — a portfolio-wide view of every `ACTIVE` loan across all clients (not filtered by one client), returning a summary with the client's name inlined to avoid N+1 `ClientService` calls; reachable from `loans_view.py`'s active-loans page.
  - **`BR-LOAN-011` (Comprobante de Pago, added this session).** `RecordPayment` now returns everything needed to issue a receipt for the debtor, rather than the client re-assembling it from what it *thought* it sent: `amount_paid`, `transfer_reference`, `paid_at`, `total_installments`, `recorded_by_name`/`recorded_by_national_id` (the authenticated operator, via `_operador_actual`, BR-AUTH-006), and `covered_installments` — the installment numbers this payment covered, which the document prints as "Cuota(s) 1 de 18" / "Cuota(s) 1,2 de 18". **The non-obvious part is where `covered_installments` comes from:** `_cuotas_cubiertas_por_pago()` derives it from the loan's real FIFO imputation (which slice of the schedule falls in the cumulative interval between the total paid before and after this payment), **not** from the `installment_number` the operator picked in the dropdown. Those differ when earlier installments are still unpaid — the money is always credited to the oldest one — and a receipt saying otherwise would contradict the schedule screen the client can see moments later. `test_record_payment_covered_installments_match_the_schedule_fifo` exists specifically to pin that agreement. Client UI: `documents.comprobante_pago_html` / `documents_docx.comprobante_pago_docx`, wired as a fifth entry in `loans_view.py`'s `_DOCUMENT_LABELS`. Unlike the other four it is **not** derivable from the loan alone — it describes one specific payment — so it is enabled only while `_last_payment`/`_last_payment_loan_id` hold a payment recorded in this session *for the loan currently open*; the server exposes no payment history, so there is deliberately no way to reprint an older receipt. Like the Cronograma it carries no draft banner (no legal clause text, only recorded figures) — the Documentos card's warning was narrowed to say so.
  - **`Loan.created_by_user_id` + Cronograma de Pago document (added this session).** `CreateLoan` now stamps the authenticated caller's user id onto the new loan (`Loan.created_by_user_id`, nullable FK to `users.id`, migration `22335ba7fdd7_add_created_by_user_id_to_loans.py` — no backfill, existing loans just read back `created_by_username=""`). `GetLoanById`/`ListClientLoans` resolve it to a username via `_nombre_usuario_creador()` and return it as `created_by_username` on `GetLoanByIdResponse` (field 23) — purely informational, not a new business rule or authorization check. This exists specifically to print an "Asesor responsable" line on a new fourth generated document, **Cronograma de Pago** (`documents.py`'s `cronograma_html`/`documents_docx.py`'s `cronograma_docx`), meant to be handed to the client as a standalone schedule copy (name + advisor + full installment table), distinct from the Liquidación (an internal-use full loan summary). Unlike the other three documents, the Cronograma carries no `_DRAFT_BANNER`/draft-banner paragraph — it has no legal clause text to review, only computed schedule data — see `documents.py`'s `_add_header(..., draft_banner=False)` param in `documents_docx.py`. Wired into `loans_view.py` exactly like the other three (`_DOCUMENT_LABELS["cronograma"]`, gated on the same `APPROVED`/`ACTIVE`/`PAID` condition as Pagaré/Contrato — a schedule isn't "confirmed enough to hand to the client" while still `PENDING`, even though it's technically computable from creation). Covered by `test_get_loan_by_id_reports_creating_advisor`/`test_get_loan_by_id_reports_no_advisor_for_loan_without_creator` in `tests/server/test_loan_interceptor_integration.py`.
  - **`BR-LOAN-012` (eliminación de un préstamo cargado por error, added this session).** `DeleteLoan(loan_id, reason)` is the **only RPC anywhere in this codebase that deletes a business row** rather than moving its status, so it is fenced on three sides rather than one:
    - **Rol:** `CREDIT_ANALYST_AND_ABOVE` in `rbac.py` — i.e. **every role except `CASHIER`**. It shipped as `MANAGER_AND_ABOVE` (one rung above origination, on the reasoning that undoing another operator's data entry is supervision); **changed 2026-08-19 by explicit business decision** — the person who mis-keys a loan is the one who notices, and forcing an escalation for every typo bought no real control. The teller stays out for the same reason as `BR-CAJA-005`: ventanilla consulta y cobra, no origina ni deshace originación. **The containment for this RPC was never really the role — it's the state**, and that is unchanged (see the two bullets below). Mirrored client-side by `rbac_ui.can_delete_loan()`, which now equals `can_originate_credit()`; guarded by a test that reads `rbac.py`'s real `METHOD_ROLES` rather than restating the expectation, plus one that pins the two client-side gates to each other.
    - **Estado:** only `PENDING`, `APPROVED` and `EXPIRED` (`_ESTADOS_ELIMINABLES` in `loan_service.py`). **The criterion is not "not finished yet" but "never moved money"** — `ACTIVE`/`PAID`/`DEFAULTED` imply a disbursement already happened, and deleting one would destroy `LoanPayment` rows that may be imputed to a `CashMovement` inside an already-closed arqueo (`CashMovement.loan_payment_id` → `loan_payments` → `loans`, BR-CAJA-003), silently changing a signed cash count. For a disbursed loan that stops paying there is `MarkDefaulted`, not deletion.
    - **Pagos:** a second, deliberately redundant check (`if prestamo.payments`) — today no eliminable state can have payments, and the check exists precisely so the *money* invariant is stated in its own right instead of surviving by coincidence of the state check. `test_delete_loan_never_destroys_a_registered_payment` builds the impossible-by-state case (an `APPROVED` loan with a payment row) specifically to keep that check alive.
    - `reason` is **required** (`INVALID_ARGUMENT` if blank): the loan row disappears, so the `AuditLog` entry (`PRESTAMO_ELIMINADO`, carrying `client_id`, previous status, capital, rate, term, first due date and the reason) is the only remaining record of what existed — it is written to be self-sufficient. `with_for_update` on the loan row, same as `ApproveLoan`/`RecordPayment`, so a concurrent payment cannot slip between the "has no payments" check and the `DELETE`. `LoanInstallmentAdjustment` rows are deleted first so the FK can't block.
    - **Client UI:** an "Eliminar préstamo" button on `loans_view.py`'s detail page, in the new `theme.danger_button_style()` (outlined red, filled only on hover — it is not a third CTA competing with the primary action). **Hidden** below MANAGER, **visible but disabled** in non-deletable states for MANAGER+, so the action's existence and its inapplicability to *this* loan both read clearly. Two dialogs on purpose: a confirmation naming the loan and warning it can't be undone, then the reason. `_on_loan_deleted` clears `_selected_loan_id`/`_detail_loan`/`_last_payment` and returns to the client's loan list — it deliberately does **not** go through `_on_action_success`, which would try to re-fetch a loan that no longer exists.
    - Side effect worth knowing: this is also the only way out of a `BR-CLI-004` deadlock. A loan mis-entered and left to reach `EXPIRED` is not `PAID`, so it blocked `DeactivateClient` **forever**; deleting it frees the client (`test_delete_loan_frees_the_client_for_deactivation`). All 15 tests live in `tests/server/test_loan_deletion.py`.

The reference is a bank transfer code / direct-debit reference / account-discount reference — free-text string, not validated beyond non-empty. This is a real server-side rule, not UI-only: `loan_service.py`'s `RecordPayment` aborts `INVALID_ARGUMENT` if it's blank on a non-cash payment, and it's persisted on `LoanPayment.transfer_reference` (`cas_server/db/models.py`, migration `3d69bf16650e_add_transfer_reference_to_loan_payments.py`). It exists because cash handling was dropped (see the `CASHIER`-tier note above) — all collection now goes through transfer/direct-debit/account-discount, and this field is the audit trail for that. The DB column itself is nullable (no backfill needed — table was empty when the column was added); the *requirement* lives in the servicer, not a DB constraint. The proto field is `loan_service_pb2.RecordPaymentRequest.transfer_reference` (field 3) — remember to pass it in any new caller of `RecordPayment`, server or client.
- `specs/dashboard/README` (added this session) — the panel/report module. Two RPCs in `protos/dashboard_service.proto`, both read-only, both implemented in `cas_server/services/dashboard_service.py`, which owns no tables of its own and aggregates over `Client`/`Loan`/`LoanPayment` at read time.
  - **`GetDashboardStats`** (no request fields), `CASHIER_AND_ABOVE` in `rbac.py` (visible to every logged-in role, since it's just aggregate counts, not sensitive per-record data): total/active client counts plus loan counts broken out by `LoanStatusEnum` value, total disbursed capital (sum of `principal_amount` for ACTIVE/PAID/DEFAULTED loans), total outstanding balance (sum of remaining balance across ACTIVE loans, via the same amortization math `loan_service.py` uses for `GetLoanById`), and — as of `BR-DASH-001` — **total overdue amount** (`total_overdue_amount`/`overdue_loans_count`). It deliberately reuses `loan_service.py`'s private `_vencer_atrasados_y_contar_activos`/`_auditar_vencidos`/`_totales_prestamo`/`_estado_pago_prestamo` helpers rather than reimplementing BR-LOAN-003's lazy-expiry check or BR-LOAN-009's overdue walk a second time — so viewing the dashboard can itself lazily flip stale APPROVED loans to EXPIRED and audit-log it, same as `ListClientLoans` already does, and the dashboard's mora total always equals the sum of each loan's own `overdue_amount`.
  - **`BR-DASH-001` (monto total de mora, added this session):** the sum of what is already due and unpaid across ACTIVE loans — what the company should collect once borrowers catch up on overdue installments. **Not the same as `total_outstanding_balance`**, which also includes every future installment not yet due; mora is always a subset of it. The dashboard shows both, side by side, with the mora tile in `theme.ERROR` red precisely so the two don't read as interchangeable.
  - **`GetPeriodReport(start_date, end_date)`** (`BR-DASH-002`, added this session), **`MANAGER_AND_ABOVE`** — gated higher than `GetDashboardStats` on purpose: a period close is management material, not an operational lookup. Mirrored client-side by `rbac_ui.can_view_period_report()` (guarded by a test that reads `rbac.py`'s real `METHOD_ROLES` table rather than restating the expectation by hand). Returns three deliberately-separated blocks: *movimiento del período* (clients/loans created, loans approved, and their capital — filtered by `Client.created_at`/`Loan.created_at`/`Loan.approved_at`), *cobranza del período* (payment count/total by `LoanPayment.paid_at`, plus loans that reached PAID — attributed to their **last payment's** date, since `Loan` has no cancellation-date column), and *situación al cierre* (active loans, outstanding, mora), which is a snapshot of **now**, not of the period's last day — both the UI caption and the generated document say so explicitly. The range is inclusive at both ends (`_inicio_del_dia(fin + 1 día)` as the exclusive upper bound, so the final day counts in full); an inverted range aborts `INVALID_ARGUMENT`.

- `specs/cash/README` (added this session) — the caja module. Five RPCs in `protos/cash_service.proto`, implemented in `cas_server/services/cash_service.py` (Spanish, per the language-split convention), owning two tables of its own.
  - **The session a call operates on always comes from the token, never the request.** No RPC takes a cashier id; only `CloseCashSession` takes an optional `session_id`, for a MANAGER+ closing a caja a cashier left open (`BR-CAJA-003`). This is why `cash_service.py` is the **one servicer that does not tolerate `claims is None`** — `_credenciales_o_abortar()` aborts `UNAUTHENTICATED` instead, since there is no meaningful "caja" without a cashier. Consequence for tests: there is deliberately **no `test_cash_service.py`** calling the servicer directly (it couldn't authenticate); all 40 tests live in `tests/server/test_cash_interceptor_integration.py`, driving a real `grpc.Server` with `AuthInterceptor` + `LoanServicer` (the latter because `BR-CAJA-004` crosses both services).
  - **`BR-CAJA-002`'s one-open-session-per-cashier rule is a partial unique index**, not a servicer check: `Index("uq_cash_session_open_por_usuario", "user_id", unique=True, postgresql_where=text("status = 'OPEN'"))` in `models.py`. Two concurrent opens would each do their own SELECT and miss each other (the ES-006 §3.1 race class); the loser now gets `ALREADY_EXISTS` via `confirmar_o_duplicado`. Closing frees the cashier to open the next shift, since the index only covers `OPEN` rows.
  - **The arqueo's expected amount is recomputed server-side** from `opening_amount` + movements, then persisted alongside the counted amount and the difference (`BR-CAJA-003`). All three are stored even though two are derivable, because a closed arqueo is a historical record — recomputing it later would let a subsequent adjustment change an already-signed close. `CloseCashSession`/`RegisterCashMovement`/the cash path of `RecordPayment` all take `with_for_update` on the `CashSession` row so a movement can't slip in between computing the expected and closing.
  - **`BR-CAJA-004` is the one cross-service rule:** `loan_service.py` imports `obtener_sesion_abierta`/`registrar_cobro_en_efectivo` from `cash_service.py` (one-way — `cash_service.py` imports nothing from `loan_service.py`, so no cycle). The caja is looked up and locked **after** the `Loan` row (consistent lock ordering) but **before** the `LoanPayment` insert, so a cash payment with no open caja leaves nothing behind. Charges/informational fields are untouched; a transfer payment does not touch the caja at all.
  - **`BR-CAJA-005` changed an existing authorization boundary**, which is unusual for this codebase — see the note under `rbac.py` in "Request flow" point 3. `cas_client/rbac_ui.py` mirrors it with `is_teller()`, `can_originate_credit()` and `can_supervise_cash_sessions()`; the last two are guarded by tests that read `rbac.py`'s real `METHOD_ROLES` rather than restating the expectation by hand.
  - **The teller collects installments from inside the Caja screen** — `CashView` takes a `ClientServiceClient` and a `LoanServiceClient` besides its own, and its "Cobro de cuotas" card walks buscar cliente → elegir préstamo (`ACTIVE` only) → elegir cuota → cobrar → emitir comprobante. This is why `main_window.py` now hoists a single `LoanServiceClient` and passes the same instance to both `LoansView` and `CashView`, the way `ClientServiceClient` was already shared. `LoansView` keeps its own payment flow for the other roles: both call `RecordPayment` with the same rules, only the entry point differs. Two deliberate inversions from `LoansView`: **Efectivo is the first payment method here** (this screen *is* the till, so cash is the normal case), and the client list responds to a **single** click rather than a double click, because it's a repetitive task rather than navigation. Non-obvious construction order trap: the payment-method combo must be populated **after** the reference field exists — the first `addItem()` moves the index from -1 to 0 and fires the handler that touches it.
  - Client UI is `cas_client/views/cash_view.py` — one page with a totals row (inicial / ingresos / egresos / cobros de cuotas / esperado), an apertura card shown only when the caja is closed, the cobro card and a movimientos card + table shown only when it's open, a cierre card whose counted-amount field is **pre-filled with the expected amount** (the normal case is that it balances; the server recomputes and compares regardless), and an arqueo history with a date-range filter. Hide-don't-disable throughout, same convention as the sidebar's "Usuarios" item. The view never computes the expected amount itself — it always displays the server's `expected_amount`, because that's the number the close is measured against. `main_window.py`'s `_Sidebar.set_role()` now **returns the landing nav item** for the role (Caja for a teller, Dashboard for everyone else) instead of always forcing Dashboard, and `_NAV_INDEX` is derived from `NAV_ITEMS` so adding a screen doesn't require updating a separate literal dict.

## Testing

`tests/conftest.py` runs every test against the **real** Postgres database configured in `cas_server/.env` (not sqlite — models use Postgres-native `UUID`/`Enum` types) and truncates `audit_logs`, `revoked_tokens`, `users`, `cash_movements`, `cash_sessions`, `loan_payments`, `loan_installment_adjustments`, `loans`, `clients` after each test. This means:
- Postgres must be up and migrated (`cd cas_server && alembic upgrade head`, see the note on migration commands above) before running the suite.
- Don't add tests that assume a mocked/in-memory DB or that expect state to survive across tests.
- If a new table is added, it must be added to that `TRUNCATE` list or leftover rows will leak between tests.

`tests/server/test_interceptor_integration.py` is the pattern for RBAC/auth coverage on new RPCs: it spins up a real `grpc.server` with `AuthInterceptor` wired in (mirroring `cas_server/server.py` exactly) and drives it over an actual channel, rather than calling servicer methods directly — this is what actually exercises metadata-based auth. `test_client_interceptor_integration.py`, `test_loan_interceptor_integration.py`, `test_dashboard_interceptor_integration.py` and `test_cash_interceptor_integration.py` follow the same pattern for the newer services. **For the caja that pattern isn't a preference but the only option** — `cash_service.py` aborts `UNAUTHENTICATED` when there are no claims (the shift it operates on comes from the token), so a direct-servicer test could not authenticate; there is deliberately no `test_cash_service.py`. Its fixture also registers `LoanServicer` alongside `CashServicer`, since `BR-CAJA-004` spans both.

`tests/server/test_loan_deletion.py` is a deliberate exception to the "one integration file per service" layout: BR-LOAN-012's interesting coverage is not "who may call it" (the pattern of `test_loan_interceptor_integration.py`) but *which loans it refuses to delete and why*, so it gets its own file with its own fixture. It still drives a real `grpc.Server` + `AuthInterceptor`, because `DeleteLoan` reads the actor from the token for its audit entry.

`tests/client/` holds `cas_client`-side tests — `test_rbac_ui.py`, `test_formatting.py` (the `DD/MM/AAAA` date helpers and the UTC→local conversion), `test_documents_identity.py` (the CREDIMED UME legal-identity block and the EXPIRED→"Rechazado" label, guarding against a silent revert to the old placeholders) and `test_documents_payment_method.py` (`BR-CAJA-004`'s medio-de-pago rows on the Comprobante de Pago). All are pure functions — no Qt, no gRPC, no DB. `test_rbac_ui.py` covers `rbac_ui.py` (`role_at_least`/`tier_label`/`can_edit_interest_rate`/`is_teller`/`can_supervise_cash_sessions`, plus a guard test that `FIXED_INTEREST_RATE` still matches `cas_server/config.py`'s `LOAN_FIXED_INTEREST_RATE`, and two that compare `can_originate_credit()` against `rbac.py`'s real `METHOD_ROLES` table rather than a hand-copied expectation). These have no Qt/gRPC dependency, so no new fixtures were needed. **Non-obvious gotcha**: `tests/conftest.py`'s `clean_db` fixture is `autouse=True` and applies to every test under `tests/`, including `tests/client/` — so running the full `pytest` suite truncates `users`/`clients`/`loans`/etc. even though these particular tests never touch the DB. If manually-seeded demo/fixture data needs to survive a test run (e.g. before a walkthrough/demo), re-seed it *after* running `pytest`, not before.

## Deployment model (docs/ES-004)

Bare-metal LAN deployment, no containers: one machine runs both `cas_server` and a client; others connect over the local subnet. PostgreSQL and `cas_server` run as native OS services — as of 2026-08-19 this is no longer aspirational, `cas_server` really is an NSSM-wrapped Windows service (see the `CASServer` bullet below). Config is via `.env` files — `cas_server/.env` (`POSTGRES_*`, `GRPC_HOST`, `GRPC_PORT`, `JWT_SECRET_KEY`, all required except host/port which default) and `cas_client/.env` (`GRPC_SERVER_HOST`, `GRPC_PORT`). `.env.example` at repo root documents the full var set; per-package `.env.example` files show what each side actually reads.

**This session stood up the first real LAN deployment** (server machine hostname `DESKTOP-5H7BABS`) and confirmed a second PC could connect end-to-end, closing out item 2 from "Recommendations for the next session" below (TLS was previously opt-in/off by default; it's now actually turned on for this deployment):
- `cas_server/.env` has `GRPC_HOST=0.0.0.0` and `GRPC_TLS_CERT_FILE`/`GRPC_TLS_KEY_FILE` pointing at `certs/server.crt`/`certs/server.key` (self-signed via `certs/openssl.cnf`, valid until 2036) — the server binds the secure port, not the insecure fallback.
- **A Windows Firewall inbound rule was required and didn't exist by default** (`CAS Server gRPC 50051`, TCP, all profiles) — binding `0.0.0.0` alone does not make Windows accept connections from other PCs on the LAN. `scripts/setup_server_admin.ps1` (not committed — deployment-machine-specific, same convention as the `.bat`/`.vbs` launchers below) creates the rule and restarts the server; it needs to run from an elevated PowerShell, because the running server process lives in Windows Session 0 and can't be signaled (`Stop-Process`) from a standard user token.
- **Client PCs connect by the server's hostname (`DESKTOP-5H7BABS`), not its LAN IP.** The IP is DHCP-assigned with a 24h lease and isn't reserved on the router, so it can change and would break both the TLS certificate's Subject Alternative Name and every client's `GRPC_SERVER_HOST` at once. The hostname resolves without any DNS server of our own — **and the mechanism is the router's DNS, not NetBIOS/LLMNR as originally assumed here**: `192.168.100.1` registers the hostnames it hands out over DHCP, verified this session with `Resolve-DnsName DESKTOP-5H7BABS -Server 192.168.100.1`. That is why resolution keeps working with Windows' network profile set to "Público" (which disables LLMNR/NetBIOS discovery) and why it self-heals when the server's lease changes its IP. `certs/openssl.cnf`'s `alt_names` now includes `DNS.2 = DESKTOP-5H7BABS` alongside the pre-existing `localhost`/IP entries so TLS hostname verification passes; `cas_client/.env.example`'s default `GRPC_SERVER_HOST` was changed from `127.0.0.1` to this hostname pattern to match.
- The first `ADMIN` user (`Crediume1`) was seeded via `seed_admin.py` — a fresh clone/install otherwise has zero users and nobody can log in from any PC.
- `docs/CONFIGURACION_CLIENTE_LAN.md` (new) is the step-by-step for setting up an additional client PC: clone/pull, venv, copy `certs/server.crt` **out-of-band** (never `server.key`; `certs/` stays gitignored as a whole — it was force-committed just once as a one-off transfer method for the first client PC, then removed again in a follow-up commit once that PC had it), fill in `cas_client/.env`, run `start_client.vbs`.
- **`cas_server` runs as the Windows service `CASServer` (added 2026-08-19), so it survives the operator logging off.** Until then it was started by hand from an elevated console and lived in the interactive session, so closing that session killed the server for every client PC at once. Installed and reconfigured by `scripts/install_service_admin.ps1` — committed, and unlike the other deployment scripts it derives every path from its own location (`$PSScriptRoot`), so it works on any clone; it needs an elevated PowerShell plus `nssm.exe`, whose location is the script's `-Nssm` parameter (kept outside the repo on this machine). The service wraps `.venv/Scripts/python.exe -m cas_server.server` through NSSM, starts automatically at boot, and **declares a dependency on `postgresql-x64-16`** — without it the server wins the boot race, cannot open the database and dies before Postgres has finished starting. It also restarts itself 5s after a crash and rotates `logs/server.log` at 10MB (that log grew unbounded before, which mattered less when the process was only up while someone was logged in). The script is idempotent: run it again to reconfigure instead of uninstalling first.
- `start_client.vbs` is now the one deployment launcher that *is* checked in — it was rewritten to resolve `.venv`/the repo root from its own script location (`WScript.ScriptFullName`) instead of a hardcoded absolute path, so the same file works regardless of where a client PC clones the repo to. **`start_server.bat` was deleted (2026-08-19)** — it predated the `CASServer` service and, run while the service was up, its `python` lost the race for port 50051 and died appending a traceback to the very `logs/server.log` the service writes to, which read like a server crash but wasn't one. **`scripts/setup_server_admin.ps1` is now committed as well**, cut back to the single thing it should do: create the firewall rule. Its old second half killed whatever was listening on 50051 — i.e. the service's own process — and launched `start_server.bat`, so once the service existed it produced exactly the port collision it was meant to prevent; the hardcoded machine paths went out with that half, which is what had kept the file out of git.

- **Times are shown in the operator's local zone, not UTC (fixed 2026-08-18).** `formatting.a_hora_local()` is the single conversion point: a **naive** datetime is read as UTC (which is exactly what `Timestamp.ToDatetime()` hands back, since the server writes `datetime.now(timezone.utc)` everywhere), an aware one is converted from whatever zone it carries. `fecha_hora()` goes through it, and so do both document modules — do **not** reintroduce a bare `.ToDatetime().strftime(...)` at a call site; that is the bug this replaced, and it printed the wrong hour on a receipt handed to a borrower.
- **Date format: the UI is `DD/MM/AAAA`, the wire is ISO (changed this session).** `cas_client/formatting.py` owns the whole translation — `fecha()` (ISO → `DD/MM/AAAA`, display-only, returns unparseable input unchanged rather than raising, since it feeds read-only labels/table cells), `fecha_a_iso()` (what the user typed → ISO, passes already-ISO through, and deliberately returns *invalid* input unchanged so the server produces the authoritative `INVALID_ARGUMENT` instead of the client silently "fixing" or blanking it), `fecha_hora()` for datetime columns, and `DISPLAY_DATE_PLACEHOLDER` for form placeholders. **The proto contract and `common.analizar_fecha()` still speak ISO — do not "fix" the server to accept `DD/MM/AAAA`**; the translation belongs at the UI edge only, and `test_period_report_rejects_a_malformed_date` exists to pin that. Every date-bearing call site was converted: `clients_view.py` (fecha de nacimiento, vencimiento de cédula), `loans_view.py` (primer vencimiento, schedule "Vencimiento" column, installment dropdown), `users_view.py` (último acceso), and both document modules. Covered by `tests/client/test_formatting.py`.
- Build on the shared widgets rather than duplicating: `BaseView` (`cas_client/widgets/base_view.py` — padding + title), `FormInput` (`cas_client/widgets/form_input.py`), `Toast` (`cas_client/widgets/toast.py` — user-facing error/info messages), `AsyncWorker` (`cas_client/widgets/async_worker.py` — generic worker-thread wrapper for any gRPC call, added alongside the client/loan views so new RPC call sites don't need a bespoke `QThread` subclass like `login_view.py`'s original `_LoginWorker`). `cas_client/widgets/card.py` holds `card()`/`section_label()`/`stat_tile()`/`labeled_field()` — promoted from what used to be `_card()`/`_section_label()`/`_stat_tile()` private duplicates in `loans_view.py` and `clients_view.py` once `dashboard_view.py` became a third caller needing the same pattern (per this file's own long-standing note to do so at that point). `labeled_field(label_text, placeholder="") -> (wrapper_widget, FormInput)` pairs a small muted caption above a `FormInput` in a `QGridLayout`-friendly wrapper — use it instead of a bare `FormInput` for any form field where placeholder-only text (which disappears once the user types) would leave the field's meaning ambiguous once filled in.
- **Table columns: use `size_columns(table, stretch_column=N)`** (`cas_client/widgets/table.py`, added this session alongside the existing `style_table()`). Call sites used to set `Stretch` on one column and leave every other at Qt's default 100px section width, which silently clipped any header longer than that — the amortization schedule rendered "Saldo restante (Gs)" as "Saldo restante (" (visible in `Templates y Detalles/Ajustes en la Tabla de Datos.png`). `ResizeToContents` measures the header text too, so a column is never narrower than its own title. **One exception worth knowing:** a column whose cells hold a widget via `setCellWidget` (the schedule's "Ajustar" button) can't be measured this way — `ResizeToContents` consults the item delegate, not the cell widget — so that column is set `Fixed` at a width derived from a probe `QPushButton`'s own `sizeHint()`, not a magic number that would break under a different font.
- **A row of more than ~3 controls must be a `ResponsiveGrid`, not a `QHBoxLayout`.** `wrap_scrollable()` disables horizontal scrolling on purpose, so anything wider than the viewport is *clipped with no way to reach it* — not scrollable. That is how `loans_view.py`'s detail page ended up with "Registrar pago" off-screen at the app's own 900×560 minimum (see this session's UI note above). When adding a toolbar or form row, check it at 900×560, not just maximised. **Two rows of 2 controls is also a valid answer, and is what `loans_view.py`'s search page uses** (buscador + "Buscar cliente" arriba, "Ver préstamos activos" + "Nuevo préstamo" alineados a la derecha abajo) — it was a fixed 4-control `QHBoxLayout` until 2026-08-19. Don't "unify" it into a single `ResponsiveGrid`: that grid splits its width into equal cells, which would cap the search field at ~1/4 of the row instead of letting it stretch (it goes 501px → 967px between a 900px and a 1366px window). **Measure with the real platform, not `QT_QPA_PLATFORM=offscreen`** — offscreen has no Comfortaa/Inter and falls back to much wider tofu glyphs, which overstated this page's minimum as 816px when the real figure was 462px. That gap is still worth designing for, though, since neither font is bundled (see the fonts note above): the wide-fallback case is what a deployment machine without them actually looks like.
- **Comboboxes go through `card.labeled_combo()`** (which applies `theme.combo_box_style()`), never a bare `QComboBox()`. An unstyled combo takes the *system* palette rather than this app's — the same trap `flat_button_style()` documents — and its drop-down popup is a separate widget that needs styling of its own. **Populate it after any field its `currentIndexChanged` handler touches exists**: the first `addItem()` moves the index from -1 to 0 and fires the handler.
- **Tables get `set_empty_message()`** alongside `style_table()`/`size_columns()`, so an empty result reads as a sentence rather than a blank white rectangle.
- **Long create/detail pages need `wrap_scrollable()`** (`cas_client/widgets/scroll_area.py`): a page widget added straight into a `QStackedWidget`/`BaseView.content_layout` gets resized to fill exactly the visible viewport, and once its content's minimum size exceeds that (e.g. `ClientsView`'s ~18-field create form), Qt compresses every child below its padded size instead of growing the window — visually this looks like overlapping/illegible fields, not a clipped scrollbar-missing page. `ClientsView`/`LoansView`'s create and detail pages are wrapped (`self._stack.addWidget(wrap_scrollable(self._build_create_page()))`); mirror this for any new page whose field count isn't small and fixed (list/table pages and the read-only schedule page are fine as-is since `QTableWidget` scrolls itself).
- Every gRPC call from the UI thread must run on a worker thread with a loading indicator shown while in flight; gRPC errors must be translated to friendly messages (each view has its own `_friendly_message`, since what e.g. `NOT_FOUND`/`FAILED_PRECONDITION` should say differs per action), never shown as raw tracebacks or status codes. Validate required fields client-side before dispatching the request.
- UI copy is in Spanish (e.g. "Cerrar sesión", "Iniciar sesión") — match this in new views. Code identifiers (variables, function/class names) stay in English on the client side — this is a deliberate split from the server's `client_service.py`/`loan_service.py`, see point 7 under "Request flow" above.
