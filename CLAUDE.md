## Project status

Five servicers, each registered in `cas_server/server.py` and covered by `cas_server/security/rbac.py`: `AuthService` (login/logout/reset/user management), `ClientService` (CRUD + KYC), `LoanService` (lifecycle + amortización), `DashboardService` (read-only aggregates + reports), `CashService` (caja). The PySide6 client covers all five: `login_view`, `dashboard_view`, `clients_view`, `loans_view`, `cash_view`, `users_view` (ADMIN), navigated from the sidebar in `cas_client/main_window.py`.

`.ai/skills/` holds a project-specific Skills registry (`INDEX.md`, `SKILL_POLICY.md`, one `SKILL.md` per topic). Consult it per `SKILL_POLICY.md` before changing code, and keep it in sync with this file when domain entities, state machines, the authorization model or the financial constants change (`domain/`, `authorization/` and `financial-rules/` have each drifted into an aspirational model once already).

**This dev machine can run the whole system, including the server suite** — the "client-only PC, no Postgres" note that stood here for several sessions was **wrong**, and it is why `tests/server/` went unrun for months while changes piled up. It has PostgreSQL 17 on **port 5433** (not the default 5432, which is why a `Test-NetConnection 5432` check says "closed") and a populated `cas_server/.env` pointing at `ds10_cas_db`. Verify before assuming otherwise: `Get-Service *postgres*` and `Get-NetTCPConnection -State Listen`.

**How to run the suite without destroying the demo data.** `tests/conftest.py` TRUNCATEs after every test and refuses to start when the target database has rows (it names the counts and how to proceed). `load_dotenv()` does not override real environment variables, so the clean way is a scratch database:
```bash
# once: create ds10_cas_test, then
cd cas_server && POSTGRES_DB=ds10_cas_test python -m alembic upgrade head && cd ..
POSTGRES_DB=ds10_cas_test pytest -q
```
Full suite verified this way on 2026-09-16: **487 passed**, including BR-LOAN-016 and the two migrations (`d4f7c2a91b08`, `f1c93a7b52de`) applied to a fresh schema.

**Server-side tests rot with the calendar.** Two failures found on that first real run were literal future dates that the calendar had overtaken (`first_due_date="2026-09-01"` against a loan created today, which the server correctly rejects) — not product defects. Derive such dates from `datetime.now()`; `tests/server/test_loan_service.py` still hardcodes `"2026-10-01"` in three places and will fail the same way after that date.

## Commands

Setup (repo root, `.venv` activated):
```bash
pip install -r requirements.txt
```

Regenerate gRPC stubs after editing any `protos/*.proto` (writes into both `cas_server/` and `cas_client/`):
```bash
python scripts/generate_protos.py
```

Run the server **in development** (binds `GRPC_HOST:GRPC_PORT` from `cas_server/.env`; TLS is active whenever `GRPC_TLS_CERT_FILE`/`GRPC_TLS_KEY_FILE` are set, which they are on the deployment machine):
```bash
python -m cas_server.server
```

**On the deployment machine, do not run that command** — `cas_server` is the Windows service `CASServer` there, and a second process loses the race for port 50051 and dies, appending a traceback to the service's own `logs/server.log` that reads like a crash. Use an elevated PowerShell: `Get-Service CASServer` / `Stop-Service CASServer` / `Start-Service CASServer`.

Run the client: `python -m cas_client.main`

First ADMIN (a fresh install has zero users and nobody can log in): `python -m cas_server.scripts.seed_admin <username> <password>`

Migrations — **run from inside `cas_server/`**, not the repo root: `alembic.ini`'s `script_location = migrations` is resolved against the *current working directory*, so `alembic -c cas_server/alembic.ini …` from the root fails with `Path doesn't exist`.
```bash
cd cas_server && alembic upgrade head && cd ..
```

Tests (need a real local Postgres via `cas_server/.env`, see Testing): `pytest`, `pytest tests/server/test_auth_service.py::test_login_locks_after_five_failures`, …

Lint/format: `black cas_client cas_server tests` and `flake8`.

## Architecture

Client-server over gRPC (`docs/ES-000_Engineering_Specification.md`):
- **`cas_client/`** — PySide6 desktop app. Presentation + client-side validation only; never touches the DB, always goes through `cas_client/grpc_client.py`.
- **`cas_server/`** — business logic, deep validation, persistence. RPCs answer standard gRPC codes.
- **`protos/`** — source of truth for the contract.
- **PostgreSQL** — system of record, reached only from `cas_server` via SQLAlchemy.

### Generated stub imports (non-obvious gotcha)

`protoc` runs with no `package` option, so the generated `*_pb2*.py` import each other flatly (`import auth_service_pb2`). They are generated straight into `cas_server/`/`cas_client/`, and each package's `__init__.py` does `sys.path.insert(0, os.path.dirname(__file__))` so those imports resolve. Application code follows the same convention — `import auth_service_pb2`, not `from cas_server import …`. Don't "fix" it.

### Request flow

1. `cas_server/server.py` builds a `grpc.server` with a single `AuthInterceptor` (`cas_server/security/interceptor.py`) and registers the five servicers.
2. The interceptor runs on every RPC: `rbac.PUBLIC_METHODS` pass; everything else needs a valid `authorization: Bearer <jwt>` that decodes, isn't in `revoked_tokens`, and whose role is in `rbac.allowed_roles(method)`. It stashes `TokenClaims` in a `ContextVar` (`security/current_user.py`) for that call only.
3. **New RPCs must be added to `rbac.py` explicitly** — an unlisted method is denied by default, not open by accident. Reuse the named tiers (`CASHIER_AND_ABOVE`, `CREDIT_ANALYST_AND_ABOVE`, `MANAGER_AND_ABOVE`) instead of ad-hoc `frozenset`s. **`rbac.py` answers "which method", never "which rows"**: *which* loans may be deleted lives in `loan_service.py` (BR-LOAN-012) and the two cash asymmetries live in `cash_service.py`'s `_es_supervisor()`.
4. Service methods open `SessionLocal()` per call, commit themselves, and write an `AuditLog` row for security-relevant actions. `client_service.py`/`loan_service.py`/`cash_service.py` share helpers from `services/common.py` (`analizar_uuid`, `analizar_decimal`, `ip_remota`, `a_marca_tiempo`, `id_actor_actual`, `confirmar_o_duplicado`) — follow `common.py` for new services, not the older English `auth_service.py` (whose `_commit_or_conflict` is now just an alias to `confirmar_o_duplicado`). `confirmar_o_duplicado` maps an `IntegrityError` to `ALREADY_EXISTS` **only** when `pgcode == "23505"`; other constraint failures propagate instead of being mislabeled as duplicates.
5. Client side: `grpc_client.py` wraps the stubs and re-raises `grpc.RpcError` as `AuthError`/`ApiError` (`.code`/`.message`); views translate that into a message and never show a traceback or a status code. Every client/loan/dashboard/cash call takes `access_token` as its first argument (`AuthClient.login` is the only public one). `cas_client/session.py`'s `Session` is a mutable holder created once by `MainWindow` and passed into the views before login, updated in place. `main_window.py` constructs **one** `ClientServiceClient` and **one** `LoanServiceClient` and shares each instance across the views that need them rather than opening extra channels. Long calls run on `widgets/async_worker.py`'s `AsyncWorker`, driving a `QProgressBar`.
6. **Client-side role gating is UX only.** `cas_client/rbac_ui.py` mirrors `rbac.py`'s tiers **by hand** (no shared source between the two processes) to enable/disable buttons; the server re-checks everything. Keep the two in sync manually, and guard new gates with a test that reads `rbac.py`'s real `METHOD_ROLES` instead of restating the expectation.
   - **Niveles shown to users** (`tier_label()`): `CASHIER`→"Cajero", `CREDIT_ANALYST`→"Estándar", `MANAGER`→"Agente de Créditos", `ADMIN`→"Administrador".
   - **The cashier's navigation is a separate list, not a prefix of everyone else's**: `_TELLER_NAV_ITEMS = ("Caja", "Clientes", "Préstamos")` and `is_teller()` is `role == "CASHIER"` exactly — deliberately not `not role_at_least(…)`, because the teller is a job, not a rung on the ladder. "Caja" is also shown to MANAGER/ADMIN (they supervise arqueos) but not to CREDIT_ANALYST.
7. **Language split (server only):** `client_service.py`, `loan_service.py`, `cash_service.py`, `amortization.py` and `common.py` are Spanish end-to-end — locals, docstrings, `context.abort()` messages and `AuditLog.action` strings (`"PRESTAMO_CREADO loan_id=…"`). `auth_service.py` and the security layer stay English. Fixed by the wire contract and therefore English regardless: proto-generated symbols, servicer class/method names, field names, and the `LoanStatusEnum` string values — translate the sentence around them, not the identifiers. **`cas_client` is not part of this**: English identifiers, Spanish UI copy.

### Connection health (client ⇄ server, one setting in two files)

Five channels stay open for an 8-hour session; idle TCP flows were being dropped by the router's NAT and by Wi-Fi power management, and neither end noticed until a click hung on retransmission timeouts. HTTP/2 PING fixes both halves (keeps the NAT entry alive, gives gRPC its own liveness signal, reconnects in the background in ~40 s).
- **`cas_client/config.py`'s `GRPC_KEEPALIVE_TIME_MS` (30 s) must be ≥ `cas_server/config.py`'s `GRPC_MIN_PING_INTERVAL_WITHOUT_DATA_MS` (10 s).** gRPC's server default for the latter is 5 min, so configuring **only** the client earns `GOAWAY / ENHANCE_YOUR_CALM / too_many_pings` and a deliberate disconnect — i.e. strictly worse than the original bug. Verified empirically; `tests/client/test_connection_keepalive.py` pins the relationship. If dropped sessions ever recur, check this *pair* before suspecting the network.
- `grpc.keepalive_permit_without_calls=1` is what makes the rest useful — the link dies precisely when no RPC is in flight.
- **Every RPC goes through `grpc_client._invoke()`** (it replaced ~31 duplicated `try/except grpc.RpcError` blocks): per-call timeout `GRPC_CALL_TIMEOUT_SECONDS` (20 s — without it an unreachable server hung `AsyncWorker` forever) plus `wait_for_ready=True`, so a call landing inside a reconnect waits instead of failing `UNAVAILABLE`. `wait_for_ready` delays sending and never re-sends, so it is as safe for `RecordPayment` as for a read.
- **`DEADLINE_EXCEEDED` is handled in `AsyncWorker`, not per view.** `session.CONNECTION_LOST_MESSAGE` deliberately states the operation *was not recorded* — a cashier whose payment fails needs to know whether re-charging would double-post. `LoginView` uses its own `_LoginWorker` and got the branch by hand.
- **Session expiry, same choke point.** BR-AUTH-003's JWT lasts 8 h with no refresh, so a client left open outlives its token. `AsyncWorker.run()` checks `_is_expired_session(exc)` *before* the per-view `error_translator`, emits `session.session_events.expired` and reports `SESSION_EXPIRED_MESSAGE`; `MainWindow._on_session_expired()` clears the `Session`, returns to `LoginView` and calls `notify_session_expired()`. It does **not** call `Logout` (the rejected token is the only one it could send) and guards on `access_token` so simultaneous failures tear down once. **`LoginView` is deliberately excluded** — `UNAUTHENTICATED` there means wrong password, not expiry — and **`UNAVAILABLE` must never be treated as expiry**, or a briefly-down server ejects the operator and discards the form they were filling. `tests/client/test_session_expiry.py` pins both distinctions.
- **`cas_client/connection_status.py` + the "● Conectado / ● Sin conexión" pill in `HeaderBar`** subscribes to the channel's own connectivity state (`Channel.subscribe`); it does not poll. `IDLE` counts as connected on purpose — an idle channel is healthy. Only the Auth channel is watched (all five point at the same host, and Auth is the only one that exists before login).
- **TLS is forced.** `_create_channel` raises `ConfigurationError` rather than silently falling back to `grpc.insecure_channel`: no `GRPC_TLS_CA_FILE` against a non-local host → refuse (escape hatch `GRPC_ALLOW_INSECURE=1`); a configured cert/key path that isn't a file → refuse, naming the path. The silent downgrade previously showed up only as `SSL_ERROR_SSL: WRONG_VERSION_NUMBER` in the server log and a generic "No se pudo conectar" for the operator. `cas_client/main.py` catches it around `MainWindow()` and shows a `QMessageBox.critical`, since the `.vbs` launcher opens no console. Credentials are loaded once via `_ssl_channel_credentials()` (`lru_cache`), not per client. Covered by `tests/client/test_grpc_channel_config.py`.
- **`scripts/diagnostico_cliente.py` is the tool to run on a client PC** — it imports only `cas_client`, so it works where the test suite can't: `.env`, name resolution, TCP 50051, TLS handshake, then a real `Login` with a nonexistent user expecting `UNAUTHENTICATED` (the only step that proves interceptor + servicer + Postgres are alive, not just that a socket opens). Note `ping DESKTOP-5H7BABS` **fails by design** from a client PC (mDNS answers a link-local IPv6 address and the firewall drops ICMP) even though the app connects fine — don't chase it.

### Business modules

`specs/` is authoritative for business logic — read the relevant spec before implementing.

#### `specs/authentication/README`
RBAC roles (CASHIER, CREDIT_ANALYST, MANAGER, ADMIN), Argon2 hashing, lockout after 5 failures, 8-hour JWTs with no refresh. Tunables in `cas_server/config.py`, each tagged with its `BR-AUTH-*` id.
- **`BR-AUTH-005`**: no self-registration — `CreateUser`/`ListUsers` are ADMIN-only; UI is `users_view.py`.
- **`BR-AUTH-006`**: operators register `first_name`/`last_name`/`national_id`, so documents can name a real person (the Cronograma's "Asesor responsable", the Comprobante's "Registrado por"). Nullable at DB, enforced in the servicer, no backfill — pre-existing users fall back to their `username`. Two deliberate choices: `users.national_id` has **no** UNIQUE constraint (unlike `clients.national_id`, so `confirmar_o_duplicado` never has to guess which constraint failed), and `seed_admin.py` still takes the personal data as *optional* args — it exists to create the first ADMIN when nobody can call `CreateUser` yet.

#### `specs/clients/README`
KYC: unique `national_id`/`email` (`BR-CLI-001`), 18+ at registration (`BR-CLI-002`), `national_id` immutable except by an audited ADMIN action (`BR-CLI-003`), soft-delete only when no non-`PAID` loans exist (`BR-CLI-004`).
- **`BR-CLI-005`**: two personal references (nombre/parentesco/teléfono) + one employment reference (empleador/cargo/teléfono/antigüedad), required at `CreateClient` and kept in sync on `UpdateClient`. Columns nullable at DB, requirement in the servicer.
- **`BR-CLI-006`**: free-text `source_of_funds` ("Origen de fondos"), required the same way.
- **`BR-CLI-008` — `DeleteClient(client_id, reason)` deletes the row for real**, unlike `DeactivateClient`. By explicit business decision **any** client may be deleted, with no exception for the state of their loans — deliberately unlike `DeleteLoan` (BR-LOAN-012), which excludes the three states that moved money. That forces a cascade inside the same transaction: the client's loans, their `LoanPayment`s and their `LoanInstallmentAdjustment`s. **A `CashMovement` imputed to one of those payments is *not* deleted** — only its `loan_payment_id` is nulled — because it may be counted in an already-closed, signed arqueo (BR-CAJA-003), and deleting it would silently change that close. `CREDIT_ANALYST_AND_ABOVE`, same criterion as `DeleteLoan`: whoever can load a client is who notices the mistake. `reason` required — the row disappears, so the `CLIENTE_ELIMINADO` audit entry is all that remains.
- **`BR-CLI-007` (extended profile) was REMOVED and the id is retired, not reused.** Its 7 optional fields are gone from the proto (numbers `reserved`), the model, the servicer, `clients_view.py` and the tests; the migration drops the columns and **the stored values are lost** (the downgrade recreates them empty). None was required or fed a rule, and they made the longest form longer.

#### `specs/loans/README`
Lifecycle PENDING → APPROVED → ACTIVE → PAID/DEFAULTED/EXPIRED. Max 3 active loans per client (`BR-LOAN-001`); 40%-of-income installment cap (`BR-LOAN-002`); 30-day expiry on undisbursed approvals (`BR-LOAN-003`), checked **lazily on read/write** (no cron/scheduler exists anywhere in this codebase). Amortization math is the pure, I/O-free `services/amortization.py`. `EXPIRED` is labelled "Rechazado"/"Rechazados" in the UI and in documents (label only — the enum and `expired_loans_count` are unchanged).

- **`BR-LOAN-013` — sistema alemán *as this entity defines it*. Do not "correct" it into the textbook one.** `calcular_cronograma` makes both components constant: capital `financiado / term`, and interest `financiado * rate / 12` computed **on the original amount, never on the declining balance**. Every installment is equal (the last absorbs the rounding cents); total interest is exactly `financiado * monthly_rate * term`. The first version of this change charged interest on the outstanding balance — the textbook reading — and the entity rejected it explicitly: on the 7.000.000 Gs / 12-month reference loan that is 3.150.000 Gs of interest instead of 1.706.250 Gs. It is a pricing decision, not a formula detail. It is also **not** the French system (constant installment, interest decreasing inside it), which is what this module computed until 2026-08-26. Consequences not to touch in isolation: BR-LOAN-002 reads `cronograma[0]`, which with equal installments is simply the representative one; BR-LOAN-008's adjustment re-splits the remaining **capital** and never touches the interest; and the Pagaré/Contrato promise "cuotas iguales" and interest "calculado sobre el monto original del préstamo" (`test_signed_instruments_*` fail if either drifts). **The schedule is not persisted** — it is recomputed from principal/rate/term on every read, so a change here is retroactive over the live portfolio.
- **`BR-LOAN-007` — the rate is fixed at 20% for every role, ADMIN included.** `LOAN_FIXED_INTEREST_RATE = Decimal("0.20")` is the **legal maximum on interest itself** (= 1,667% mensual). `_tasa_estandar_o_abortar()` accepts an empty `interest_rate` (the normal case — the form has no rate field) or exactly the constant, and **rejects** anything else instead of silently substituting: creating at 20% something asked for at 10% is worse than failing. `rbac_ui.can_edit_interest_rate()` returns `False` for everyone and is kept, rather than deleted, so the answer "no, not the Administrator either" is written where someone would re-add the field. The clause text never hardcodes a monthly figure — `formatting.rate_percent_mensual()` derives it from the loan's own stored annual rate, so the documents and the schedule cannot disagree.
- **`BR-LOAN-006` — charges are financed, not informational, and capped at 40% of capital.** `_monto_financiado()` (`principal_amount + _total_cargos`) is the **single** definition of what the schedule amortises, and all four `calcular_cronograma` call sites go through it, so the schedule, the remaining balance, BR-LOAN-009's mora, the FIFO imputation and BR-LOAN-002's cap move together. Three amounts read alike and are **not** interchangeable: `amount_to_disburse` (= `principal_amount`, what the client gets in hand), `total_credit_with_charges` (capital + cargos, what the instalments amortise and the interest accrues on — it used to mean "total a pagar + cargos", so old figures are not comparable), and `total_to_pay` (that plus `total_interest`). `GetLoanByIdResponse` carries all of them plus `installment_amount`, computed server-side so the screen and both document formats can't each derive them differently.
  - **`LOAN_MAX_CHARGES_RATIO = Decimal("0.40")`**: the 4 charge fields together may not exceed `principal_amount * 0.40 / 12 * term_months` (the same term-prorating BR-LOAN-013 uses for interest). Enforced by `_tope_cargos()`/`_validar_tope_cargos()` at all three write paths — `CreateLoan` and `UpdateLoanProposal` before touching the DB, `UpdateLoanCharges` after fetching the loan — aborting `INVALID_ARGUMENT` naming the peso ceiling for that loan. **This is deliberately not one combined 60% check**: the 20% interest cap and the 40% charges cap are two independent ceilings on two different things (a rate baked into `interest_rate`, a sum of operator-entered pesos). The entity's total cost of credit is 20% legal interest + up to 40% financed charges = 60% annual.
  - **BR-LOAN-006's 40% cargo cap and BR-LOAN-002's 40% income cap are the same number by coincidence, not the same rule** — changing one must not assume it fixes the other.
  - `UpdateLoanCharges` revalidates BR-LOAN-002: it is the one path that could otherwise blow past the income cap after the proposal was validated.
  - **A prior request asked to make the extra charges "disfrazado" — to have the Pagaré declare only the 20% and hide the rest as undisclosed profit. That was refused, and the same request should get the same answer.** The Pagaré/Contrato are signed debt instruments; printing a smaller figure than what is collected is deceptive lending. They declare the real `total_credit_with_charges`, and changing the cap never changes what the signed document discloses.
  - `test_charges_are_capitalized_into_what_the_borrower_must_repay` is the deliberate inversion of an older `test_charges_do_not_affect_record_payment_payoff`, which protected exactly the opposite invariant. Fixture amounts in `test_loan_service.py`/`test_loan_interceptor_integration.py` are chosen to sit under (or exactly at — the ceiling is inclusive) this cap: when it moves, rework the numbers rather than relaxing the rule, and note that `test_update_loan_charges_rejects_charges_that_break_the_income_cap` needs an amount that clears the cargo cap *and* breaks the income cap, or it aborts on the wrong rule.
- **`BR-LOAN-004` — editable proposal.** While `PENDING`, terms + guarantee + charges are editable via `UpdateLoanProposal`, which **is authoritative** (sending guarantee/charges empty clears them) and re-validates BR-LOAN-002, but deliberately does *not* re-check BR-LOAN-001 (PENDING loans never count as active) and never touches `interest_rate`. Editing stops at `ApproveLoan`, so approval stays a real gate. It also aborts `NOT_FOUND`/`FAILED_PRECONDITION` when the client is missing or has no `declared_monthly_income` — without those guards it multiplied `None * Decimal` and answered `UNKNOWN`, which every view flattens to "Ocurrió un error inesperado". `first_due_date` is NOT NULL on `Loan`, auto-computed at `CreateLoan` (`created_at + LOAN_DEFAULT_FIRST_DUE_DAYS`); it is the only calendar-date concept in amortization, passed as `calcular_cronograma`'s optional `fecha_primer_vencimiento` anchor (omitting it keeps the function calendar-agnostic).
- **`BR-LOAN-005` — one guarantee per loan**, flat nullable `guarantee_type`/`guarantee_amount` on `Loan` (both set or both blank). Guarantees and charges are flat columns, not child tables + dynamic add/remove rows: every multi-field group in this codebase is fixed-cardinality.
- **`BR-LOAN-008` — `UpdateInstallmentAmount`** (`MANAGER_AND_ABOVE`, `ACTIVE`-only) stores a row in `LoanInstallmentAdjustment` (`UNIQUE(loan_id, installment_number)`) applied as an override when the schedule is recomputed, rather than mutating it. The last installment is never adjustable (it absorbs the remainder). Locks the `Loan` row `with_for_update`, because two concurrent adjustments each validated only against already-committed ones and their combined effect was never checked.
- **`BR-LOAN-009` — `payment_status`** ("AL_DIA"/"CUOTA_VENCIDA") walks the schedule FIFO-matched against real payments, looking only at installments already past due. Distinct from `remaining_balance`, which is the whole loan regardless of what's overdue.
- **`BR-LOAN-010` — `RecordPayment(installment_number=…)`**: the server recomputes that installment's exact pending amount itself and **ignores any client-supplied `amount`**, so it can't be spoofed. `installment_number=0` keeps the free-form mode.
- **`BR-LOAN-011` — Comprobante de Pago.** `RecordPayment` returns everything the receipt needs (`amount_paid`, `transfer_reference`, `paid_at`, `total_installments`, `recorded_by_name`/`_national_id`, `covered_installments`). **`covered_installments` comes from the loan's real FIFO imputation (`_cuotas_cubiertas_por_pago()`), not from the `installment_number` the operator picked** — money is always credited to the oldest unpaid installment, and a receipt saying otherwise would contradict the schedule screen. The *fresh* receipt is still gated on `_last_payment`/`_last_payment_loan_id` (the payment recorded in this session, for the loan on screen); reprinting an older one goes through BR-LOAN-016 and is marked as a duplicate.
  - **That pin is a correctness guard, not bookkeeping.** The ticket takes the loan number from the screen and the amounts from the payment in memory, so an un-pinned receipt mixes two collections. `cash_view.py` cleared it when the *client* changed but not when the *loan* did (a client may have 3 active loans, BR-LOAN-001) — fixed with `_comprobante_vigente()`/`_sync_receipt_buttons()`, which also re-enable the buttons on returning to the loan just collected.
  - **Both views clear their session state on every operator change** (`CashView.set_user` / `LoansView.apply_role` → `clear_session_state()`). The views are built once and survive logout, so the next teller on a shared window used to find the previous one's client on screen and their receipt still printable. `tests/client/test_view_session_state.py` pins both rules with a real (offscreen) widget.
- **`BR-LOAN-012` — `DeleteLoan(loan_id, reason)` destroys a loan instead of moving its status**, so it is fenced on three sides (it was the first such RPC; `RemoveInstallmentAdjustment` and `DeleteClient` came later, each with its own fencing):
  - **Rol** `CREDIT_ANALYST_AND_ABOVE` — every role except `CASHIER`. It shipped as `MANAGER_AND_ABOVE` and was lowered by explicit business decision: the person who mis-keys a loan is the one who notices. The teller stays out for the same reason as BR-CAJA-005.
  - **Estado** `PENDING`/`APPROVED`/`EXPIRED` only (`_ESTADOS_ELIMINABLES`). **The criterion is "never moved money", not "not finished yet"** — deleting a disbursed loan would destroy `LoanPayment` rows that may be imputed to a `CashMovement` inside an already-closed arqueo, silently changing a signed cash count. For a disbursed loan that stops paying there is `MarkDefaulted`.
  - **Pagos**: a deliberately redundant `if prestamo.payments` check, so the money invariant is stated in its own right instead of surviving by coincidence of the state check; `test_delete_loan_never_destroys_a_registered_payment` builds the impossible-by-state case to keep it alive.
  - `reason` is required: the row disappears, so the `PRESTAMO_ELIMINADO` audit entry (client, previous status, capital, rate, term, first due date, reason) is the only remaining record. `with_for_update`; adjustments deleted first so the FK can't block. Side effect: it is the way out of a BR-CLI-004 deadlock without destroying the client (an EXPIRED mis-entry blocked `DeactivateClient` forever).
- **`BR-LOAN-014` — `RevertDefault(loan_id, reason)`**, same tier as `MarkDefaulted` (whoever sets the flag can clear it; the two `allowed_roles()` sets are pinned equal by test). It closed a real dead end: `RecordPayment` requires `ACTIVE`, `DeleteLoan` excludes every state that moved money, and anything but `PAID` blocks `DeactivateClient` — so a defaulted loan and its client were frozen permanently even when the borrower caught up. It returns to `ACTIVE` because that is by construction where it came from, and **does not assert the borrower is current**: `payment_status` keeps reporting `CUOTA_VENCIDA` if it is. The loan's *status* is what the entity decided; `payment_status` is what the borrower owes today.
- **`BR-LOAN-015` — `RemoveInstallmentAdjustment(loan_id, installment_number, reason)`**, same tier as `UpdateInstallmentAmount`, one client-side gate for both buttons. **Re-typing the original amount is not equivalent, which is why this exists**: `UpdateInstallmentAmount` only upserts, the re-split lands cents on later installments, the row stays flagged `is_adjusted` forever and the audit log records an adjustment that never happened. **Removing one adjustment can legitimately be refused while others remain** — a small adjustment removed makes the balance drop faster, so a later, larger one can overshoot; the servicer recomputes and aborts `FAILED_PRECONDITION` on a negative saldo. `reason` required; the audit entry carries the amount the deleted adjustment had.
- **`RecordPayment` requires `transfer_reference` only for `payment_method=TRANSFERENCIA`** (empty = TRANSFERENCIA, so pre-existing callers are unaffected). `EFECTIVO` skips it and requires an open caja instead (BR-CAJA-004). Real server-side rule, persisted on `LoanPayment.transfer_reference`; the DB column is nullable, the requirement lives in the servicer.
- **`BR-LOAN-016` — `ListLoanPayments(loan_id)`, the payment history** (`CASHIER_AND_ABOVE`, same tier as `RecordPayment`: in ventanilla the client asks "¿ya pagué?" and the teller answers). Before it, a payment was visible **only to whoever registered it, and only until they changed screen** — a ticket that jammed could not be reprinted and a colleague's collection showed up as nothing but a smaller balance. Each entry repeats the figures of *that* receipt — amount, its own FIFO imputation, and the running total and balance **after it** — **reconstructed** from the schedule and the payments in order, for the same reason the schedule isn't persisted: they are a function of those two, and a stored copy could contradict the computation. The honest caveat: the schedule is recomputed from the loan's *current* data, so an installment adjusted after the fact (BR-LOAN-008) can shift a reconstructed imputation — which is why **a reprinted document declares itself a reprint** (`documents.CobroHistorico` + `es_reimpresion()`) instead of passing for the original. The ticket number is deliberately *unchanged* on a duplicate: it identifies the collection, not the impression, so the duplicate can still be matched to the original in an arqueo.
  - `RecordPayment` now also returns `payment_id`, which is what ties the receipt issued at the time to the one reprinted later.
  - **`LoanPayment.recorded_by_user_id`** (nullable FK, **no backfill**, same criterion as `Loan.created_by_user_id`/`disbursed_at`) stores who collected. It was only in the `AuditLog` as free text, which neither the history nor a reprinted receipt can read. Payments predating the column report `""` and the paper says so rather than crediting the collection to whoever reprints it.
  - Client UI: a "Cobros registrados" card on `loans_view.py`'s detail page (full history + reprint of ticket and A4) and a compact table inside `cash_view.py`'s collection card (history + ticket reprint). Both load with the loan, so a colleague's payment appears just by opening it. The fresh-payment ticket (no reprint mark) is a separate button from the row reprint.
- **`Loan.created_by_user_id`** (nullable FK, no backfill) stamps the authenticated caller at `CreateLoan`, resolved to `created_by_username` for the Cronograma's "Asesor responsable". Purely informational.
- **`Loan.disbursed_at`** exists because the period report could not total disbursements — `DisburseLoan` only flipped the status, so `GetPeriodReport` had no date to filter on and reported capital *solicitado* and *aprobado* (decisions) but never the money that left. **`approved_at` is not a substitute and neither is the status**: up to 30 days can pass between approval and disbursement, or it may never happen, and an `ACTIVE` loan today may have been disbursed in an earlier period. Nullable with **no backfill** (stamping old loans with `approved_at` would invent a disbursement in the wrong period); they stay out of every range, and the all-time figure is still `GetDashboardStats.total_disbursed`, computed by status. It totals `principal_amount`, **not** `_monto_financiado` — charges are capitalised, not handed over.
- `ListActiveLoans` (any authenticated role) is a portfolio-wide view of every `ACTIVE` loan with the client's name inlined to avoid N+1 `ClientService` calls.
- **Carga por "Cuota deseada" (client-side only).** `cas_client/loan_math.py`'s `cargo_para_cuota_objetivo()` inverts BR-LOAN-013's installment to find the *gasto administrativo* that yields a negotiated installment, filling that (still hand-editable) charge field; `_suggest_admin_fee()` also pre-fills it with the computed ceiling once capital and plazo are entered, but only while it is still empty, so it never overwrites a manual entry or a loaded proposal. It is invertible only because both components are constant and proportional to the financed amount. **The excess becomes a charge, never interest** — the rate is fixed by law. Over the ceiling it **refuses instead of clamping**, naming the highest reachable installment (writing a charge the server would reject is worse than saying it can't be done); below the no-charge installment it also refuses. **The charge rounds DOWN to whole guaraníes**: rounding up crossed the ceiling by cents and charged more than asked. `tests/client/test_loan_math.py` checks the inverse against `calcular_cronograma` rather than hand-written amounts — a hand-written number only proves the formula didn't change, not that it still matches the server.
- `loans_view.py`'s `_build_proposal_form(prefix, …)` builds the same single form for the create and edit pages, `_proposal_fields(prefix)` reads it, and `_CHARGE_FIELDS` is the one list the form, the summary and the RPC call all walk. The edit page used to be three cards with three independent save buttons — actively misleading once charges moved the instalment. The detail page leads with `_SUMMARY_ROWS` + `_charges_breakdown_text()` (capital / cargos / total del crédito / interés / total a pagar / cuota / a desembolsar), the three read aloud in `theme.PRIMARY`. The rate line says "Interés legal" and points at the charges card below; it deliberately does **not** spell out the 40%/60% arithmetic on screen (that stays in `specs/loans/README` and code comments).
- `_apply_action_gate()` puts the *reason* in each action button's tooltip — wrong state (naming the current one and the applicable ones) and/or insufficient level, worded with `tier_label()`. "Desembolsar" reads as a missing option because it needs **both** `APPROVED` and MANAGER+; the boundary itself is a business decision, not a UI fix.

#### `specs/dashboard/README`
Read-only; `dashboard_service.py` owns no tables and aggregates over `Client`/`Loan`/`LoanPayment` at read time. It deliberately reuses `loan_service.py`'s private helpers (`_vencer_atrasados_y_contar_activos`, `_auditar_vencidos`, `_totales_prestamo`, `_estado_pago_prestamo`, `_proxima_cuota_impaga`) instead of reimplementing BR-LOAN-003's lazy expiry or BR-LOAN-009's overdue walk — so viewing the dashboard can itself flip stale APPROVED loans to EXPIRED, and its totals always equal the sum of each loan's own figures.
- **`GetDashboardStats`** (`CASHIER_AND_ABOVE` — aggregate counts, not per-record data): client/loan counts by status, total disbursed capital, total outstanding balance, and **`BR-DASH-001`'s `total_overdue_amount`/`overdue_loans_count`**. **Mora is not `total_outstanding_balance`** — the latter includes every future installment; mora is always a subset. Both tiles are shown side by side, mora in `theme.ERROR`, precisely so they don't read as interchangeable.
- **`GetPeriodReport(start_date, end_date)`** (`BR-DASH-002`, **`MANAGER_AND_ABOVE`** — a period close is management material, not an operational lookup). Three deliberately separated blocks: *movimiento* (by `Client.created_at`/`Loan.created_at`/`approved_at`, plus `loans_disbursed`/`principal_disbursed` by `disbursed_at`), *cobranza* (by `LoanPayment.paid_at`, plus loans that reached PAID, attributed to their **last payment's** date since `Loan` has no cancellation column), and *situación al cierre*, which is a snapshot of **now**, not of the period's last day — both the caption and the document say so. The range is inclusive at both ends; an inverted range aborts `INVALID_ARGUMENT`.
- **`GetClientPaymentStatusReport(only_overdue)`** (`BR-DASH-003`, **`CREDIT_ANALYST_AND_ABOVE`** — one rung below the period report: chasing overdue clients is the analyst's daily work; the teller is out for the BR-CAJA-005 reason). One row per client with a **live portfolio** (at least one `ACTIVE` or `DEFAULTED` loan — a client with no loans has no payment status and would only lengthen the collections list). **`INCUMPLIDO` outranks `CUOTA_VENCIDA` outranks `AL_DIA`**: DEFAULTED is a state an operator declared, not something deduced from a schedule, so it wins even when the rest of the portfolio is current. Saldo/mora/próximo vencimiento come from the *same* helpers `GetLoanById` uses — the date a collections agent quotes on the phone has to be the one the loan screen shows. **The response totals describe the rows returned, not the whole portfolio** (with `only_overdue` they legitimately differ from the panel's; the caption and both documents say so). Ordered by mora desc, then name, so two runs agree. Snapshot of `generated_at`, no date range. **It is the only document in the app that prints landscape** (8 columns).
- Client UI: `dashboard_view.py` — stat-tile grid refreshed on every `showEvent`, plus the reports cards (hidden entirely below the required role, hide-don't-disable). `_refresh_stats()` tags each request with a generation counter so a stale in-flight refresh can't overwrite a newer one.

#### `specs/cash/README`
`OpenCashSession` / `GetCurrentCashSession` / `RegisterCashMovement` / `CloseCashSession` / `ListCashSessions` (`BR-CAJA-001`…`005`) in `cash_service.py` (Spanish), over two own tables (`cash_sessions`, `cash_movements`).
- **The session a call operates on always comes from the token, never the request.** No RPC takes a cashier id; only `CloseCashSession` takes an optional `session_id`, for a MANAGER+ closing a caja a cashier left open (`BR-CAJA-003`). This is why `cash_service.py` is the **one servicer that does not tolerate `claims is None`** — `_credenciales_o_abortar()` aborts `UNAUTHENTICATED`. Consequence: there is deliberately **no `test_cash_service.py`** (a direct-servicer test could not authenticate); all its tests live in `test_cash_interceptor_integration.py`, whose fixture also registers `LoanServicer` because BR-CAJA-004 spans both.
- **`BR-CAJA-002`'s one-open-session-per-cashier rule is a partial unique index** (`postgresql_where=text("status = 'OPEN'")`), not a servicer check: two concurrent opens would each SELECT and miss each other; the loser now gets `ALREADY_EXISTS`. Closing frees the cashier for the next shift.
- **The arqueo's expected amount is recomputed server-side** and then persisted alongside the counted amount and the difference, even though two are derivable — a closed arqueo is a historical record, and recomputing it later would let a later adjustment change an already-signed close. `CloseCashSession`/`RegisterCashMovement`/the cash path of `RecordPayment` all take `with_for_update` on the `CashSession`.
- **`BR-CAJA-004` is the one cross-service rule**: `loan_service.py` imports `obtener_sesion_abierta`/`registrar_cobro_en_efectivo` from `cash_service.py` — one-way, no cycle. The caja is locked **after** the `Loan` row (consistent lock ordering) but **before** the `LoanPayment` insert, so a cash payment with no open caja leaves nothing behind. A transfer payment never touches the caja.
- **`BR-CAJA-005` changed an existing authorization boundary**, which is unusual here: `CreateClient`/`UpdateClient`/`CreateLoan`/`UpdateLoanProposal`/`UpdateLoanGuarantee`/`UpdateLoanCharges` moved from `CASHIER_AND_ABOVE` to `CREDIT_ANALYST_AND_ABOVE`, because the teller became a real job — ventanilla consulta y cobra, no origina crédito. Tests that asserted the old boundary were rewritten, not deleted: **if a test name in git history says `allows_cashier`, read this rule before "restoring" it.**
- **The teller collects installments from inside the Caja screen** (`CashView` takes a `ClientServiceClient` and a `LoanServiceClient` besides its own): buscar cliente → préstamo `ACTIVE` → cuota → cobrar → comprobante. `LoansView` keeps its own payment flow for the other roles; same rules, different entry point. Two deliberate inversions there: **Efectivo is the first payment method** (this screen *is* the till) and the client list responds to a **single** click (repetitive task, not navigation). Construction-order trap: populate the payment-method combo **after** the reference field exists — the first `addItem()` moves the index from -1 to 0 and fires the handler.
- The view never computes the expected amount itself; it always displays the server's `expected_amount`, because that is the number the close is measured against. The cierre card pre-fills the counted amount with it (the normal case is that it balances; the server recomputes regardless).
- **Ticket de cobro de 80 mm**: raw ESC/POS bytes (`cas_client/escpos.py`) streamed straight to the Windows spooler as a `RAW` job (`cas_client/printing.py`, via `win32print`) — **not** `QTextDocument`/`QPrinter` any more, and no `QPrintDialog`. A fourth button on the "Cobro de cuotas" card. No proto/server/DB change — `RecordPaymentResponse` already carried everything. Traps:
  - **This replaced a Qt/GDI approach that never worked on the real hardware.** The caja's actual printer ("Printer POS-80", `USB\VID_1FC9&PID_2016`) ships as Windows' generic **"Generic / Text Only"** driver — confirmed with `scripts/diagnostico_impresora_ticket.py` that it (and the two built-in "Virtual"/"Universal Print Class Driver" alternatives) silently **ignore any custom `QPageSize` and force A4**, so the old `apply_ticket_page()`/`render_ticket()` machinery could never have printed a correct ticket on this device, no matter how the page layout was built. If a future printer is a *real* GDI/PostScript device, that Qt path may work again — verify with the same diagnostic script before reintroducing it.
  - **`TICKET_PRINTER_NAME`** (`cas_client/.env`) names the exact Windows printer the ticket goes to; empty falls back to Windows' default printer. `printing.ticket_printer()`/`_printer_name()` refuse (`PrinterNotFoundError`) rather than guess if it doesn't resolve to an installed printer.
  - **CP437 has no em dash/curly quotes.** `escpos._sanear()` downgrades them (em/en dash → `-`, curly quotes → straight) before encoding, so the entity's address (which does use an em dash for the A4/HTML documents) doesn't print as a literal `?` on the ticket.
  - Font A is monospaced at **48 columns** (`escpos._COLUMNAS`, the typical default at 80 mm/203 dpi) — right-aligned amounts are built with `str.rjust()`, not an HTML table (`documents.ticket_cobro_html()`'s `_ticket_filas()`, which the ESC/POS path does **not** use — it builds its own text layout in `escpos.ticket_cobro_escpos()`, reusing only `documents.py`'s data helpers). If a real ticket's columns wrap early or crowd the right edge, this is the first constant to adjust, after visually checking the paper.
  - **No logo and no colour, deliberately**: a thermal head is monochrome, a colour bitmap dithers and is slow, and several of these drivers don't print images at all (doubly true for a `RAW` text stream, which carries no image data at all). Pinned by test.
  - **The closing message deliberately says nothing about amounts changing.** The A4 Comprobante ends with "el saldo restante puede variar…"; on the ticket the entity asked for that to go — it is the paper the client walks out with, and a caveat about costs varying reads as a reservation about the payment just taken. The caveat stays on the archival A4.
  - **`documents.ticket_cobro_html()` is no longer what gets printed**, but it's kept: `tests/client/test_ticket_cobro.py`/`test_reimpresion.py` still exercise it directly, and nothing else currently reads it. Don't assume it's dead code.

## Testing

`tests/conftest.py` runs everything against the **real** Postgres from `cas_server/.env` (not sqlite — models use Postgres-native `UUID`/`Enum`) and truncates `audit_logs`, `revoked_tokens`, `users`, `cash_movements`, `cash_sessions`, `loan_payments`, `loan_installment_adjustments`, `loans`, `clients` after each test:
- Postgres must be up and migrated first.
- Don't add tests assuming a mocked/in-memory DB or state surviving across tests.
- **A new table must be added to that TRUNCATE list** or rows leak between tests.

`tests/server/test_*_interceptor_integration.py` is the pattern for RBAC/auth coverage: a real `grpc.server` with `AuthInterceptor` wired in, driven over an actual channel — that is what exercises metadata-based auth. `tests/server/test_loan_deletion.py` is a deliberate exception to one-file-per-service: BR-LOAN-012's interesting coverage is *which loans it refuses to delete and why*, not who may call it.

`tests/client/` is pure functions — no Qt, no gRPC, no DB (`test_rbac_ui.py`, `test_formatting.py`, `test_documents_identity.py`, `test_documents_payment_method.py`, `test_ticket_cobro.py`, `test_loan_math.py`, `test_grpc_channel_config.py`, `test_connection_keepalive.py`, `test_session_expiry.py`). Two gotchas:
- `conftest.py`'s `clean_db` fixture is `autouse=True` for **everything under `tests/`**, so a full `pytest` run truncates the DB even though these tests never touch it. Re-seed demo data *after* a run, not before.
- `conftest.py` imports `cas_server.config`, which hard-requires `POSTGRES_*`, so on a client-only PC every test dies at collection. Use `pytest tests/client --noconftest`.

## Coding standards (docs/ES-000)

Python 3.11+ (dev venv 3.12), `black` + `flake8` (`setup.cfg`: 100-char lines; generated `*_pb2*.py` and migration `versions/` excluded, mirrored in `pyproject.toml`'s `[tool.black] extend-exclude`). Type hints mandatory on 100% of server and client functions.

## Deployment model (docs/ES-004)

Bare-metal LAN, no containers: one machine runs `cas_server` + a client, others connect over the subnet. Config via `.env` (`cas_server/.env`: `POSTGRES_*`, `GRPC_HOST`, `GRPC_PORT`, `JWT_SECRET_KEY`, TLS paths; `cas_client/.env`: `GRPC_SERVER_HOST`, `GRPC_PORT`, `GRPC_TLS_CA_FILE`). Live deployment: server `DESKTOP-5H7BABS`.
- `GRPC_HOST=0.0.0.0` with `GRPC_TLS_CERT_FILE`/`KEY_FILE` → the server binds the secure port. Self-signed via `certs/openssl.cnf`, valid until 2036; `certs/` is gitignored — copy `server.crt` to client PCs **out-of-band**, never `server.key`.
- **A Windows Firewall inbound rule is required and does not exist by default** (`CAS Server gRPC 50051`, TCP, all profiles). `scripts/setup_server_admin.ps1` creates it and does only that — its old second half killed whatever listened on 50051 (i.e. the service itself) and relaunched the since-deleted `start_server.bat`, producing exactly the port collision it was meant to prevent.
- **Client PCs connect by hostname, not by LAN IP.** The IP is DHCP with a 24 h lease; the hostname resolves through **the router's own DNS** (`192.168.100.1` registers the names it hands out — verified with `Resolve-DnsName`), **not** NetBIOS/LLMNR, which is why it keeps working with the network profile set to "Público" and self-heals when the lease changes the IP. `certs/openssl.cnf`'s `alt_names` includes `DNS.2 = DESKTOP-5H7BABS`. An IP fallback only passes TLS verification for an IP in the cert's SAN.
- **`cas_server` runs as the Windows service `CASServer`** so it survives the operator logging off. Installed/reconfigured (idempotently) by the committed `scripts/install_service_admin.ps1`, which derives every path from `$PSScriptRoot` and takes `nssm.exe`'s location as `-Nssm`. It **declares a dependency on `postgresql-x64-16`** — without it the server wins the boot race, can't open the DB and dies; it restarts 5 s after a crash and rotates `logs/server.log` at 10 MB.
- `start_client.vbs` is the one committed launcher (resolves `.venv`/repo root from `WScript.ScriptFullName`, so it works wherever a PC clones to). `docs/CONFIGURACION_CLIENTE_LAN.md` is the step-by-step for a new client PC; its setup check is a TCP probe to 50051, not a ping (see `diagnostico_cliente.py` above).
- **Deployment scope depends on what changed**: touching only `cas_client/` (e.g. the documents modules) ships by `git pull` on client PCs alone — no service restart, no migration. Touching `protos/`, `cas_server/` or the schema needs `alembic upgrade head` and a `CASServer` restart on the server machine too.

## Client UI conventions (docs/ES-003)

- **Single window**: fixed 220px sidebar (`_Sidebar`, clickable, `item_selected`) + a `QStackedWidget` content area — no separate windows. `ClientsView`/`LoansView`/`CashView` nest one level deeper, each a `BaseView` wrapping its own stack of sub-pages rather than opening dialogs. `_Sidebar.set_role()` returns the landing nav item for the role (Caja for a teller, Dashboard otherwise); `_NAV_INDEX` is derived from `NAV_ITEMS`.
- **Brand "CREDIMED UME"** (`theme.BRAND_NAME`). Logo/icon bitmaps resolve through `cas_client/assets.py` (`LOGO_FULL_PNG`, `LOGO_MARK_PNG`, `APP_ICON_ICO`, plus `logo_full_data_uri()` for embedding in the QTextDocument PDFs) — never hardcode asset paths in views.
- **Palette ("CrediMed", `theme.py`)**: navy `#2B407B` (`PRIMARY`/`SIDEBAR_BG`), lime `#8CC63F` (`ACCENT`), emerald `#2E9344` (`SUCCESS`), gray `#808285` (`TEXT_MUTED`/`BORDER`). Reference the constants, never hex literals. **`ACCENT` is background-only** — lime text on white is <2:1 contrast; pair a lime background with navy text, never white. Use `theme.accent_button_style()` / `secondary_button_style()` / `danger_button_style()` / `flat_button_style()` instead of inline stylesheets. Fonts (`HEADING_FONT_FAMILY` Comfortaa, `BODY_FONT_FAMILY` Inter) are CSS fallback lists, **not bundled** — the deployment machines may not have them, which is also why `QT_QPA_PLATFORM=offscreen` measurements (tofu glyphs) overstate widths. `main.py` sets `QT_QPA_PLATFORM` only on `win32` and only when unset, so it can't clobber `offscreen`.
- **Any widget that doesn't set an explicit `color:` takes the *system* palette, not the theme** — the trap `flat_button_style()` documents. It has already produced an invisible-value bug on the loan summary and unstyled combos; set both branches of a stylesheet.
- **A row of more than ~3 controls must be a `ResponsiveGrid`, not a `QHBoxLayout`.** `wrap_scrollable()` disables horizontal scrolling on purpose, so anything wider than the viewport is **clipped with no way to reach it**. This has already put "Registrar pago"/"Eliminar préstamo" off-screen on the loan detail page and "Imprimir comprobante" off the caja's action row, both at the documented 900×560 minimum. Check new rows at 900×560, not maximised. **Two rows of 2 controls is also a valid answer** and is what `loans_view.py`'s search page uses — don't "unify" it into one grid, whose equal cells would cap the search field at ~¼ of the row instead of letting it stretch.
- **Long create/detail pages need `wrap_scrollable()`** (`widgets/scroll_area.py`). A page added straight into a `QStackedWidget` is resized to the viewport, and once its minimum exceeds that, Qt compresses every child below its padded size — which looks like overlapping/illegible fields, not a missing scrollbar. List/table pages are fine as-is (`QTableWidget` scrolls itself).
- **Tables**: `style_table()` + **`size_columns(table, stretch_column=N)`** + **`set_empty_message()`**. Leaving columns at Qt's default 100px silently clips any longer header; `ResizeToContents` measures the header text too. **Exception**: a column whose cells hold a widget via `setCellWidget` can't be measured that way (the delegate is consulted, not the widget) — set it `Fixed` from a probe button's `sizeHint()`, measuring **all** the probes when a cell can hold more than one button. `set_empty_message()`'s overlay is a child `QLabel` + resize event filter, **not** an assigned `viewport.paintEvent` — PySide6 dispatches virtuals to methods on the *class*, so the instance-attribute version fails silently.
- **Comboboxes go through `card.labeled_combo()`** (which applies `theme.combo_box_style()`, including the drop-down popup — a separate widget that does not inherit the closed field's style), never a bare `QComboBox()`. Carry enum values as `itemData` and display `tier_label()`-style labels, not raw enum names.
- Build on the shared widgets: `BaseView`, `FormInput`, `Toast`, `AsyncWorker`, and `widgets/card.py`'s `card()`/`section_label()`/`stat_tile()` (opt-in `icon_text` monogram badge)/`labeled_field()`/`labeled_combo()`. Prefer `labeled_field()` over a bare `FormInput` wherever placeholder-only text would leave the field ambiguous once filled.
- **Times are shown in the operator's local zone.** `formatting.a_hora_local()` is the single conversion point: a **naive** datetime is read as UTC (exactly what `Timestamp.ToDatetime()` returns, since the server writes `datetime.now(timezone.utc)`), an aware one is converted from its own zone. `fecha_hora()` and both document modules go through it — **never reintroduce a bare `.ToDatetime().strftime(...)`**: that bug printed the wrong hour on a receipt handed to a borrower.
- **Dates: the UI is `DD/MM/AAAA`, the wire is ISO.** `cas_client/formatting.py` owns the whole translation — `fecha()` (display, returns unparseable input unchanged since it feeds read-only labels), `fecha_a_iso()` (what the user typed → ISO; returns *invalid* input unchanged so the server produces the authoritative `INVALID_ARGUMENT` instead of the client silently "fixing" it), `fecha_hora()`, `DISPLAY_DATE_FORMAT`, `DISPLAY_DATE_PLACEHOLDER`. **Call `es_fecha_valida()` on any new date input** and mark the field with `set_error(True)` naming `DISPLAY_DATE_PLACEHOLDER`: without it the only feedback is the server's own message, which names the **wire** format and tells the operator to use a format the form never asked for. `fecha_a_iso()` accepts `-`/`.`/space separators and `AAAA/MM/DD`, but **always tries ISO first** so `2026-10-09` can never be re-read as day-first — don't reorder those attempts. **Do not "fix" the server to accept `DD/MM/AAAA`**: the translation belongs at the UI edge, `common.analizar_fecha`'s docstring records why, and `test_period_report_rejects_a_malformed_date` pins it.
- Every gRPC call from the UI thread runs on a worker thread with a loading indicator; errors are translated per view (`_friendly_message`, since what `NOT_FOUND`/`FAILED_PRECONDITION` should say differs per action), never shown raw. Validate required fields before dispatching. File save/print paths are wrapped in `try/except OSError` (`_friendly_file_error()`) so a locked destination shows a `Toast`, not a traceback.
- UI copy is Spanish; client-side code identifiers stay English (see Request flow §7).

### Generated documents

`cas_client/documents.py` (PDF, via `QTextDocument` + `QPrinter`/`QPrintDialog`) and `cas_client/documents_docx.py` (editable `.docx` via `python-docx`, so a user can hand-edit a field without regenerating) build: **Liquidación**, **Pagaré**, **Contrato**, **Cronograma de Pago**, **Comprobante de Pago**, the **ticket de cobro** (PDF path only), and the dashboard's **reporte de período** and **reporte de estado de pagos** (`liquidacion_`/`pagare_`/`contrato_`/`cronograma_`/`comprobante_pago_`/`ticket_cobro_`/`reporte_periodo_`/`reporte_estado_pagos_` + `html` or `docx`). All are built from data already fetched via existing RPCs.
- **Font sizes in a printed document go in `pt`, never `px`.** `QTextDocument` resolves a `px` font size against the **paint device's DPI**, and both output paths use `QPrinter(HighResolution)` = 1200 dpi, so `font-size: 20px` printed **0.42 mm** tall instead of 5.29 mm: the entity name, the document title and the footers came out illegible while the `pt` text beside them was fine. That was the reported "errores de tamaño en la fuente al imprimir". `margin`/`padding` in px are *not* affected (they resolve as CSS px), so the fix was `font-size` only (1px = 0.75pt). `tests/client/test_document_print_sizes.py` measures each document against a 1200-dpi and a 96-dpi printer and fails if they differ, and forbids the unit in the module — which is how the defect comes back, by copying a style from a view, where px is correct.
- **The Ficha de Cliente is a form, not a report.** Its layout follows `docs/cambios finales/Ejemplo de Ficha de Clientes.png` (another company's registration form — **structure only**, as with the Pagaré reference): numbered section bands, a bordered field grid, and a final "espacio para uso exclusivo" block. The top half is data the system already holds; the bottom half — dictamen, monto aprobado, firmas, observaciones, and the references' "Verificada" boxes — prints **blank on purpose**, because those are filled in by hand on the paper that goes into the legajo. The system does not record whether a reference was actually called, and pretending it does would be worse than leaving the box. It fits one A4 (~261 mm of ~267 usable); the DOCX carries the same decision block, since without it the file describes the application but records no decision.
- **`documents_docx.py` imports `documents.py`'s constants and row builders rather than restating them** — `_ESTADOS_LABEL`, `_COMPANY_*`, `_TERM_*`, `_filas_reporte()`, `_filas_estado_pagos()`, `filas_composicion_credito()`, `tiene_cargos_financiados()`, `_garantia_label_valor()` — an intentional same-package exception to the underscore convention, so the PDF and the DOCX of the same document cannot drift. Add new shared content the same way.
- **Legal identity** (real DNIT registration): `_COMPANY_NAME` CREDIMED UME, `_COMPANY_RUC` `1276703-4`, `_COMPANY_ADDRESS` "Ayolas c/ Acaray — Coronel Oviedo, Paraguay", `_COMPANY_PHONE` `(0984) 319243`. Deliberately separate from `theme.BRAND_NAME` (UI chrome); keep both in sync by hand. `tests/client/test_documents_identity.py` guards against a silent revert. The logo bitmaps are still the older CrediUme artwork — they are supplied design assets, not something to regenerate here.
- **The commercial terms are authorised and live in one place**, `documents.py`'s `_TERM_*`: interés compensatorio derived from the loan's own rate via `rate_percent_mensual()`, moratorio/punitorio 0,38% mensual por cuota vencida devengado desde el día **5**, exigibilidad del total a partir de **3** cuotas vencidas, jurisdicción Coronel Oviedo. **Changing a `_TERM_*` or `LOAN_FIXED_INTEREST_RATE` is a legal/commercial decision, not a code tweak** — the tests fail on a silent change, deliberately. Two wordings not to "correct": the entity defined a **single** mora rate carrying both moratory and punitive character, and acceleration is a **faculty** of the lender ("facultará a … a exigir"), not automatic.
- **There is no draft banner any more.** If a clause ever goes back to being undefined, reinstate a banner rather than shipping a blank or `[A DEFINIR]` field — `test_no_placeholder_survives_in_the_signed_instruments` fails loudly.
- **The Pagaré and Contrato declare the real `total_credit_with_charges`** with the capital + cargos breakdown spelled out (BR-LOAN-006). Declaring only the capital would describe a smaller debt than the schedule collects.
- **The Pagaré's layout imitates `docs/modelo de pagare.pdf`** (a different institution's real instrument — layout only, never content): no logo and no company header block (`_pagare_header()`), and the client identification block at the **foot**, right before the signature. The Contrato keeps the full logo + company header. Deliberately **not** copied from that reference: its "sobre saldos deudores" interest clause (BR-LOAN-013 requires "sobre el monto original"), its automatic acceleration, its per-cuota amount in words and its expanded jurisdiction clause.
- **The Contrato's cláusula Primera omits the charges phrase only when a loan has none** (`tiene_cargos_financiados()`); with charges — the normal case — the full sentence is mandatory.
- The Cronograma, the reports and the Comprobante carry no clause text, only computed figures. The Comprobante is not derivable from the loan alone (it describes one payment), hence the no-reprint rule under BR-LOAN-011.
