## Commands

Setup (from repo root, after activating `.venv`):
```bash
pip install -r requirements.txt
```

Regenerate gRPC stubs after editing any `protos/*.proto` file (writes into both `cas_server/` and `cas_client/`):
```bash
python scripts/generate_protos.py
```

Run the server (binds `GRPC_HOST:GRPC_PORT` from `cas_server/.env`, insecure port — TLS is deferred):
```bash
python -m cas_server.server
```

Run the client:
```bash
python -m cas_client.main
```

Create the first ADMIN user (needed before any login is possible):
```bash
python -m cas_server.scripts.seed_admin <username> <password>
```

Database migrations (config at `cas_server/alembic.ini`, scripts in `cas_server/migrations/`). **Run from inside `cas_server/`, not the repo root** — `alembic.ini`'s `script_location = migrations` is a relative path that Alembic resolves against the current working directory, not the ini file's location, so `alembic -c cas_server/alembic.ini ...` run from the repo root fails with `Path doesn't exist: '<repo root>/migrations'` even though that's the invocation pattern you'd expect to work:
```bash
cd cas_server
alembic upgrade head
alembic revision --autogenerate -m "message"
cd ..
```

Tests (requires a real local Postgres reachable via `cas_server/.env` — see Testing below):
```bash
pytest
pytest tests/server/test_auth_service.py
pytest tests/server/test_auth_service.py::test_login_locks_after_five_failures
```

Lint / format:
```bash
black cas_client cas_server tests
flake8
```

## Architecture

Client-server system over gRPC (see `docs/ES-000_Engineering_Specification.md`):

- **`cas_client/`** — PySide6 desktop app. Presentation + client-side input validation only; never touches the DB, always goes through a gRPC stub (`cas_client/grpc_client.py`).
- **`cas_server/`** — business logic, deep validation, persistence. RPCs return standard gRPC status codes (`OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `UNAUTHENTICATED`, `PERMISSION_DENIED`).
- **`protos/`** — source of truth for the client-server contract.
- **PostgreSQL** — system of record, accessed only from `cas_server` via SQLAlchemy.

### Generated stub imports (non-obvious gotcha)

`protoc` is invoked with no `package` option, so the generated `*_pb2.py`/`*_pb2_grpc.py` files import each other with flat statements like `import auth_service_pb2` rather than package-qualified ones. Since these files are generated straight into `cas_server/` and `cas_client/`, each package's `__init__.py` does `sys.path.insert(0, os.path.dirname(__file__))` so those flat imports resolve. Application code follows the same convention — e.g. `cas_server/services/auth_service.py` does `import auth_service_pb2`, not `from cas_server import auth_service_pb2`. Keep new service modules consistent with this pattern rather than "fixing" the imports.

### Request flow (auth vertical slice as the template for new services)

1. `cas_server/server.py` builds a `grpc.server` with a single `AuthInterceptor` (`cas_server/security/interceptor.py`) wired in, then registers `AuthServicer`, `ClientServicer`, `LoanServicer`, and `DashboardServicer`.
2. `AuthInterceptor` runs on every RPC: public methods (`rbac.PUBLIC_METHODS`) pass through; everything else needs a valid `authorization: Bearer <jwt>` metadata entry, the JWT must decode and not be in the `revoked_tokens` table, and the token's role must be in `rbac.allowed_roles(method)`. Unlisted methods are denied by default. On success it stashes `TokenClaims` in a `ContextVar` (`cas_server/security/current_user.py`) for the duration of that call only.
3. New RPCs must be added explicitly to `cas_server/security/rbac.py`'s `PUBLIC_METHODS`/`METHOD_ROLES` — an RPC with no entry there is unreachable (`UNIMPLEMENTED`/deny-by-default), not "open by accident." `rbac.py` defines named role tiers (`CASHIER_AND_ABOVE`, `CREDIT_ANALYST_AND_ABOVE`, `MANAGER_AND_ABOVE`) that mirror the seniority order implied by the specs — reuse these instead of writing out ad hoc `frozenset({...})`s per method.
4. Service methods (`cas_server/services/`) open `SessionLocal()` per call, do their own commits, and write an `AuditLog` row for security-relevant actions (login success/failure, lockout, logout, password reset, client create/update/deactivate/national-id change, loan create/approve/disburse/payment/default/expiry). `client_service.py` and `loan_service.py` share request-parsing/response-shaping helpers from `cas_server/services/common.py` (`analizar_uuid`, `analizar_decimal`, `ip_remota`, `a_marca_tiempo`, `id_actor_actual`) — `auth_service.py` predates that extraction and still inlines its own (English-named) equivalents, so follow `common.py` for any new service rather than the older auth code.
5. `LoansView` (`cas_client/views/loans_view.py`) takes both a `LoanServiceClient` and a `ClientServiceClient` in its constructor — the latter was added so the Documentos feature can fetch client contact details (name/address/phone) when rendering a document, since `LoanService` responses only carry `client_id`. `main_window.py` constructs a single `ClientServiceClient()` and passes the same instance to both `ClientsView` and `LoansView` rather than opening a second channel. On the client, `cas_client/grpc_client.py` wraps stubs and re-raises `grpc.RpcError` as an error object; views translate that into a user-facing message and never show a raw traceback or gRPC code to the user. `AuthClient` (login/logout) raises `AuthError`; `ClientServiceClient`/`LoanServiceClient` raise the more generic `ApiError` (same shape — `.code`/`.message`) since they cover more than authentication. Every client/loan RPC requires a Bearer token, so those two clients take `access_token` as the first arg on every method (`AuthClient.login` is the only public/unauthenticated call). `cas_client/session.py`'s `Session` is a small mutable holder for the post-login token/role/username; `MainWindow` creates one instance and passes it into `ClientsView`/`LoansView` at construction time (before login happens), updating it in place on login/logout so the views always see the current token without being re-created. Long-running calls run on a worker thread via the reusable `cas_client/widgets/async_worker.py`'s `AsyncWorker` (generalizes `login_view.py`'s original bespoke `_LoginWorker` so new RPCs don't need their own `QThread` subclass), driving a `QProgressBar` via signals.
6. Role-gating on the client is UX-only, not authoritative: `cas_client/rbac_ui.py`'s `role_at_least()` mirrors `rbac.py`'s tiers by hand (no shared source between the two processes) to decide which buttons to enable — e.g. "Desembolsar" needs MANAGER+, "Aprobar"/"Marcar incumplido" need CREDIT_ANALYST+, "Cambiar documento" needs ADMIN. The server re-checks everything regardless; keep `rbac_ui.py` in sync with `rbac.py` by hand when adding new gated actions.
   - **User-facing "niveles" (non-obvious mismatch with the backend enum):** the UI presents 3 tiers instead of the backend's 4 roles — `rbac_ui.py`'s `tier_label()` maps `CASHIER`→"Estándar", `CREDIT_ANALYST`→"Estándar", `MANAGER`→"Agente de Créditos", `ADMIN`→"Administrador". This reflects a product decision, not a backend change: the `CASHIER` role still exists in `RoleEnum` (see `cas_server/db/models.py`) and still works if assigned, it's just not currently given to any real user — cash handling was dropped in favor of bank transfer/direct debit/account discount (see `transfer_reference` below), so `CREDIT_ANALYST` became the de facto base/"Estándar" tier. If a 4th UI tier is ever wanted, split the `CASHIER`/`CREDIT_ANALYST` mapping in `tier_label()`.
   - **Interest-rate editability (UI-only rule):** `rbac_ui.py`'s `can_edit_interest_rate()` (true for MANAGER+) and `FIXED_INTEREST_RATE` ("0.24") drive the "Nuevo préstamo" form in `loans_view.py`: Estándar users get the rate field pre-filled and read-only, Agente de Créditos/Administrador can type any rate. This is explicitly **not** enforced server-side — `loan_service.py`'s `CreateLoan` still accepts any `interest_rate` from any role allowed to call it (`CASHIER_AND_ABOVE` in `rbac.py`). If this ever needs to be a real security boundary rather than a UX guardrail, that requires a new server-side check (and test) in `loan_service.py`, not just a client tweak.
7. **Language split (non-obvious, server-side only):** `cas_server/services/client_service.py`, `loan_service.py`, `amortization.py`, and `common.py` are written in Spanish end-to-end — local variables, docstrings, comments, `context.abort()` messages, and `AuditLog.action` strings (e.g. `"PRESTAMO_CREADO loan_id=..."`, `"CLIENTE_ACTUALIZADO client_id=..."`). `auth_service.py` (and the rest of the security layer) is still English and untouched. When extending these two services, match the Spanish convention already there; don't mix English identifiers back in. Things that stay in English regardless, because they're fixed by the wire contract or DB schema: proto-generated symbols (`*_pb2*.py`, servicer class/method names like `ClientServicer.CreateClient`, request/response field names like `client_id`/`principal_amount`), and the `LoanStatusEnum` string values returned in `status` fields (`"PENDING"`, `"APPROVED"`, etc.) — translate the sentence around them, not the identifiers themselves. **`cas_client` was not part of this — it keeps the pre-existing convention** (English identifiers, Spanish UI copy only, see "Client UI conventions" below); `clients_view.py`/`loans_view.py`/`grpc_client.py` etc. follow `login_view.py`'s existing style, not the server's.

### Business modules

Domain rules live in `specs/` and are authoritative for business logic — read the relevant spec before implementing a module:
- `specs/authentication/README` — RBAC roles (CASHIER, CREDIT_ANALYST, MANAGER, ADMIN), Argon2 password hashing, lockout after 5 failed attempts, 8-hour JWTs with no refresh. `cas_server/config.py` holds the tunable constants (`LOCKOUT_MAX_ATTEMPTS`, `JWT_EXPIRES_SECONDS`, etc.), each tagged with its `BR-AUTH-*` business rule ID in a comment. Implemented in `cas_server/services/auth_service.py`. **User management (`BR-AUTH-005`, existing functionality documented this session — it predates this session's own changes):** `CreateUser`/`ListUsers` in `auth_service.py`, both `ADMIN`-only in `rbac.py` — there is no self-registration, every operator account is created by an Administrator. Client UI is `cas_client/views/users_view.py` ("Usuarios" in the sidebar, gated behind `can_manage_users()` in `rbac_ui.py`), previously missing from this file's view inventory.
- `specs/clients/README` — KYC rules (18+, unique `national_id`/`email`, `national_id` immutable except by audited ADMIN action, soft-delete only when no non-"PAID" loans exist, and — as of `BR-CLI-005` — two personal references (name/relationship/phone each) plus one employment reference (employer/position/phone/seniority) required at registration and kept in sync on every `UpdateClient`). Implemented in `cas_server/services/client_service.py`; client UI is `cas_client/views/clients_view.py` (search/create/edit/deactivate/national-id-change). The reference columns on `Client` (`cas_server/db/models.py`) are nullable at the DB level — same pattern as `LoanPayment.transfer_reference` below — the requirement is enforced in the servicer, not a DB constraint, so no backfill was needed for the migration (`e5b966988ac9_add_client_reference_fields.py`). **`BR-CLI-006` (added this session, prompted by a gap analysis against a competing system's AML/KYC flow):** clients must also register a free-text `source_of_funds` ("Origen de fondos"), required at `CreateClient`/`UpdateClient` exactly like the reference fields — same nullable-at-DB/enforced-in-servicer pattern, migration `dafc1159158f_add_source_of_funds_to_clients.py`. This was the first of four gaps identified that session; the other three (editable credit proposals, loan guarantees, charges/insurance breakdown) are now `BR-LOAN-004`/`BR-LOAN-005`/`BR-LOAN-006` (see the `specs/loans/README` bullet below). **`BR-CLI-007` (extended client profile, closes out the gap analysis):** 7 optional fields — `national_id_expiry_date`, `marital_status`, `education_level`, `occupation`, `neighborhood`, `risk_rating`, `economic_sector` — covering the video's Datos Personales/Direcciones/Cliente tabs (Ingresos/Egresos, Propiedades, Vínculos and Comp. Accionista stayed out of scope, same reasoning as guarantees/charges below: no list-of-items precedent in this codebase). Unlike every other `BR-CLI-*`/`BR-LOAN-*` addition so far, **none of these 7 fields are required** — nothing in the video ties them to a hard rule the way AML/source-of-funds does, so `CreateClient`/`UpdateClient` accept them or not with no validation beyond `national_id_expiry_date`'s date-format check (via `analizar_fecha`, shared from `common.py`). Migration `910ca69c913b_add_extended_profile_fields_to_clients.py`. Because nothing became required, this shipped with a much smaller blast radius than `BR-CLI-006` — no existing test fixture or RPC call site needed fixing. Client UI: a new shared `_extended_profile_card()` helper in `clients_view.py` (mirrors `_reference_cards()`'s role), used on both the create and detail pages.
- `specs/loans/README` — Loan lifecycle (PENDING → APPROVED → ACTIVE → PAID/DEFAULTED/EXPIRED), max 3 active loans/client (`BR-LOAN-001`), 40%-of-income payment cap (`BR-LOAN-002`), 30-day expiry on undisbursed approvals (`BR-LOAN-003`). Implemented in `cas_server/services/loan_service.py`, with amortization math (French/annuity schedule) factored into the pure, I/O-free `cas_server/services/amortization.py`. `BR-LOAN-*` constants live in `cas_server/config.py` alongside the auth ones. Expiry (`BR-LOAN-003`) is checked lazily on read/write (mirrors the auth lockout's lazy-expiry pattern) rather than via a background job — no cron/scheduler exists in this codebase. Client UI is `cas_client/views/loans_view.py` (create/approve/disburse/record-payment/mark-defaulted, plus a read-only amortization schedule viewer) — reached either from its own client-ID search box or via "Ver préstamos" on a client's detail page in `clients_view.py` (`ClientsView.view_loans_requested` signal, handled in `main_window.py`).
  - **`BR-LOAN-004` (editable credit proposal, second gap-analysis item after `BR-CLI-006`).** While a loan is `PENDING`, its `principal_amount`, `term_months`, and `first_due_date` are editable via `UpdateLoanProposal`, which re-validates the BR-LOAN-002 40%-of-income cap against the new terms (mirrors `CreateLoan`'s own check) but deliberately does **not** re-check BR-LOAN-001 (PENDING loans never count toward the active-loan cap, per `_ESTADOS_ACTIVOS` in `loan_service.py`). Editing is blocked once `ApproveLoan` runs — this preserves approval (`CREDIT_ANALYST_AND_ABOVE`) as a real gate rather than something an edit could silently bypass; `interest_rate` is intentionally not editable by this RPC. `first_due_date` is a NOT NULL `Date` column on `Loan`, auto-computed at `CreateLoan` (`created_at + LOAN_DEFAULT_FIRST_DUE_DAYS`, default 30 days, migration `7ea55b398f13_add_first_due_date_to_loans.py` used a 3-step backfill since the column is NOT NULL). This is also the **first calendar-date concept anywhere in loan amortization** — `amortization.py`'s `calcular_cronograma` gained an optional `fecha_primer_vencimiento` anchor param (each `Cuota` gets a `fecha_vencimiento` when one is passed; existing callers that omit it are unaffected, so the function stays backward-compatible/calendar-agnostic by default). `GetAmortizationSchedule` passes the loan's `first_due_date` and returns a `due_date` per installment, shown as a "Vencimiento" column in `loans_view.py`'s schedule table.
  - **`BR-LOAN-005`/`BR-LOAN-006` (guarantees + charges/informational, third/fourth gap-analysis items — closed out the original 4-item gap analysis).** Rather than a one-to-many child table + dynamic add/remove-row Qt list (no precedent anywhere in this codebase — every existing multi-field group, e.g. `ClientsView`'s reference cards, is fixed-cardinality), both were scoped down to flat nullable columns on `Loan`, same pattern as `first_due_date`/`source_of_funds`: `guarantee_type`/`guarantee_amount` (BR-LOAN-005, one guarantee per loan, both fields must be set together or both blank) and `charge_interest_tax`/`charge_admin_fee`/`charge_cancellation_insurance`/`charge_contracted_insurance` (BR-LOAN-006, each independently optional). Migration `8e26811a6e56_add_guarantee_and_charges_to_loans.py` — plain nullable columns, no backfill needed. **Charges are deliberately informational-only**: `calcular_cronograma`, `_totales_prestamo`, `RecordPayment`'s payoff check, BR-LOAN-002's ratio validation, and the dashboard's outstanding-balance sum are all untouched — a loan with charges set still reaches `PAID` based on principal+interest alone (see `test_charges_do_not_affect_record_payment_payoff` in `tests/server/test_loan_service.py`, which exists specifically to protect this invariant). `loan_service.py` exposes a new `_total_cargos` helper and two computed response fields, `total_charges` and `total_credit_with_charges` (= `total_programado` + `total_charges`) — the latter exists so the guarantee's "monto aplicado" has something to compare against, matching the video's own workflow, without folding charges into any real collection logic. Two new single-purpose RPCs (`UpdateLoanGuarantee`, `UpdateLoanCharges`, both `CASHIER_AND_ABOVE`, both `PENDING`-only) rather than folding into `UpdateLoanProposal` — mirrors this codebase's one-RPC-per-action convention. Client UI: both live as extra cards on `loans_view.py`'s existing `_PAGE_EDIT_PROPOSAL` page, each with its own independent save button (not chained to the proposal-terms save). `documents.py`'s `liquidacion_html` gained a conditional guarantee/charges breakdown section (`_cargos_y_garantia_block`) — `pagare_html`/`contrato_html` were left untouched. **All 4 items from the original gap analysis are now implemented** (`BR-CLI-006`, `BR-LOAN-004`, `BR-LOAN-005`, `BR-LOAN-006`, `BR-CLI-007`) — see "Recommendations for the next session" below for what's next.
  - **`BR-LOAN-007` (fixed-rate enforcement, now a real server-side rule, not just UX).** `LOAN_FIXED_INTEREST_RATE = Decimal("0.24")` in `config.py`. `CreateLoan` now rejects a non-standard `interest_rate` when the caller's role is below `MANAGER` (`rbac.MANAGER_AND_ABOVE`), reading the role from `get_current_claims()` — the same mechanism `id_actor_actual` already used for audit logging. **Only fires when `claims is not None`**: direct-servicer unit tests (no `AuthInterceptor` in the call path) always see `claims=None`, so the check is skipped there by design — this mirrors `id_actor_actual`'s existing None-tolerant pattern and keeps every pre-existing `test_loan_service.py` test using arbitrary rates unaffected. The restriction is only actually exercised through `tests/server/test_loan_interceptor_integration.py` (real login → real claims), e.g. `test_create_loan_rejects_non_standard_rate_for_standard_role`/`test_create_loan_allows_manager_to_set_custom_rate`. `UpdateLoanProposal` doesn't touch `interest_rate` at all (per `BR-LOAN-004`), so no second enforcement point was needed. `cas_client/rbac_ui.py`'s `can_edit_interest_rate()`/`FIXED_INTEREST_RATE` doc comments were updated to stop saying "UI-only" — keep the two constants in sync by hand (no shared source between client/server processes, same caveat as `role_at_least`).
  - **`BR-LOAN-008`/`BR-LOAN-009`/`BR-LOAN-010` (installment-level payment tracking, existing functionality documented this session).** `BR-LOAN-008`: `UpdateInstallmentAmount` (`MANAGER_AND_ABOVE`, `ACTIVE`-only) lets an operator fix a specific installment's amount; stored as a row in `LoanInstallmentAdjustment` (one per adjusted installment, `UNIQUE(loan_id, installment_number)`) rather than mutating the computed schedule, applied as an override when `calcular_cronograma` recomputes it. The last installment is never adjustable (it always absorbs the exact remainder). `BR-LOAN-009`: `GetLoanById`'s `payment_status` ("AL_DIA"/"CUOTA_VENCIDA") walks the full schedule FIFO-matched against real payments and looks only at installments already past due — distinct from `remaining_balance`, which is the whole loan's balance regardless of what's overdue. `BR-LOAN-010`: `RecordPayment(installment_number=...)` lets a payment target one specific installment; the server recomputes that installment's exact pending amount itself (same FIFO as BR-LOAN-009) and ignores any client-supplied `amount` for that case, so the amount recorded can't be spoofed. `installment_number=0` keeps the older free-form mode. Client UI: `loans_view.py`'s "Ajustar" button per schedule row (BR-LOAN-008) and the "Cuota a pagar" dropdown next to "Registrar pago" (BR-LOAN-010, populated by fetching `GetAmortizationSchedule` and filtering to unpaid installments). `protos/loan_service.proto` also has `ListActiveLoans` (no request fields, any authenticated role) — a portfolio-wide view of every `ACTIVE` loan across all clients (not filtered by one client), returning a summary with the client's name inlined to avoid N+1 `ClientService` calls; reachable from `loans_view.py`'s active-loans page.
  - **`Loan.created_by_user_id` + Cronograma de Pago document (added this session).** `CreateLoan` now stamps the authenticated caller's user id onto the new loan (`Loan.created_by_user_id`, nullable FK to `users.id`, migration `22335ba7fdd7_add_created_by_user_id_to_loans.py` — no backfill, existing loans just read back `created_by_username=""`). `GetLoanById`/`ListClientLoans` resolve it to a username via `_nombre_usuario_creador()` and return it as `created_by_username` on `GetLoanByIdResponse` (field 23) — purely informational, not a new business rule or authorization check. This exists specifically to print an "Asesor responsable" line on a new fourth generated document, **Cronograma de Pago** (`documents.py`'s `cronograma_html`/`documents_docx.py`'s `cronograma_docx`), meant to be handed to the client as a standalone schedule copy (name + advisor + full installment table), distinct from the Liquidación (an internal-use full loan summary). Unlike the other three documents, the Cronograma carries no `_DRAFT_BANNER`/draft-banner paragraph — it has no legal clause text to review, only computed schedule data — see `documents.py`'s `_add_header(..., draft_banner=False)` param in `documents_docx.py`. Wired into `loans_view.py` exactly like the other three (`_DOCUMENT_LABELS["cronograma"]`, gated on the same `APPROVED`/`ACTIVE`/`PAID` condition as Pagaré/Contrato — a schedule isn't "confirmed enough to hand to the client" while still `PENDING`, even though it's technically computable from creation). Covered by `test_get_loan_by_id_reports_creating_advisor`/`test_get_loan_by_id_reports_no_advisor_for_loan_without_creator` in `tests/server/test_loan_interceptor_integration.py`.
  - **`RecordPayment` requires `transfer_reference`** (a bank transfer code / direct-debit reference / account-discount reference — free-text string, not validated beyond non-empty). This is a real server-side rule, not UI-only: `loan_service.py`'s `RecordPayment` aborts `INVALID_ARGUMENT` if it's blank, and it's persisted on `LoanPayment.transfer_reference` (`cas_server/db/models.py`, migration `3d69bf16650e_add_transfer_reference_to_loan_payments.py`). It exists because cash handling was dropped (see the `CASHIER`-tier note above) — all collection now goes through transfer/direct-debit/account-discount, and this field is the audit trail for that. The DB column itself is nullable (no backfill needed — table was empty when the column was added); the *requirement* lives in the servicer, not a DB constraint. The proto field is `loan_service_pb2.RecordPaymentRequest.transfer_reference` (field 3) — remember to pass it in any new caller of `RecordPayment`, server or client.
- `protos/dashboard_service.proto` — `DashboardService.GetDashboardStats` (no request fields), read-only, `CASHIER_AND_ABOVE` in `rbac.py` (visible to every logged-in role, since it's just aggregate counts, not sensitive per-record data). Implemented in `cas_server/services/dashboard_service.py`: total/active client counts plus loan counts broken out by `LoanStatusEnum` value, total disbursed capital (sum of `principal_amount` for ACTIVE/PAID/DEFAULTED loans), and total outstanding balance (sum of remaining balance across ACTIVE loans, via the same amortization math `loan_service.py` uses for `GetLoanById`). It deliberately reuses `loan_service.py`'s private `_vencer_atrasados_y_contar_activos`/`_auditar_vencidos`/`_totales_prestamo` helpers rather than reimplementing BR-LOAN-003's lazy-expiry check a second time — so viewing the dashboard can itself lazily flip stale APPROVED loans to EXPIRED and audit-log it, same as `ListClientLoans` already does. Client UI is `cas_client/views/dashboard_view.py` (stat-tile grid, fetched via `DashboardServiceClient.get_dashboard_stats` on every `showEvent`), replacing the old static welcome-label placeholder.

## Testing

`tests/conftest.py` runs every test against the **real** Postgres database configured in `cas_server/.env` (not sqlite — models use Postgres-native `UUID`/`Enum` types) and truncates `audit_logs`, `revoked_tokens`, `users`, `loan_payments`, `loans`, `clients` after each test. This means:
- Postgres must be up and migrated (`cd cas_server && alembic upgrade head`, see the note on migration commands above) before running the suite.
- Don't add tests that assume a mocked/in-memory DB or that expect state to survive across tests.
- If a new table is added, it must be added to that `TRUNCATE` list or leftover rows will leak between tests.

`tests/server/test_interceptor_integration.py` is the pattern for RBAC/auth coverage on new RPCs: it spins up a real `grpc.server` with `AuthInterceptor` wired in (mirroring `cas_server/server.py` exactly) and drives it over an actual channel, rather than calling servicer methods directly — this is what actually exercises metadata-based auth. `test_client_interceptor_integration.py`, `test_loan_interceptor_integration.py`, and `test_dashboard_interceptor_integration.py` follow the same pattern for the newer services.

`tests/client/` (new) holds `cas_client`-side tests — currently just `test_rbac_ui.py`, covering the pure functions in `rbac_ui.py` (`role_at_least`/`tier_label`/`can_edit_interest_rate`, plus a guard test that `FIXED_INTEREST_RATE` still matches `cas_server/config.py`'s `LOAN_FIXED_INTEREST_RATE`). These have no Qt/gRPC dependency, so no new fixtures were needed. **Non-obvious gotcha**: `tests/conftest.py`'s `clean_db` fixture is `autouse=True` and applies to every test under `tests/`, including `tests/client/` — so running the full `pytest` suite truncates `users`/`clients`/`loans`/etc. even though these particular tests never touch the DB. If manually-seeded demo/fixture data needs to survive a test run (e.g. before a walkthrough/demo), re-seed it *after* running `pytest`, not before.

## Coding standards (docs/ES-000)

- Python 3.11+ (dev venv is 3.12), PEP-8 via `black` and `flake8` (`setup.cfg`: 100-char lines, generated `*_pb2*.py` and migration `versions/` excluded from flake8).
- Type hints mandatory on 100% of server and client functions.

## Deployment model (docs/ES-004)

Bare-metal LAN deployment, no containers: one machine runs both `cas_server` and a client; others connect over the local subnet. PostgreSQL and `cas_server` run as native OS services (e.g. NSSM on Windows). Config is via `.env` files — `cas_server/.env` (`POSTGRES_*`, `GRPC_HOST`, `GRPC_PORT`, `JWT_SECRET_KEY`, all required except host/port which default) and `cas_client/.env` (`GRPC_SERVER_HOST`, `GRPC_PORT`). `.env.example` at repo root documents the full var set; per-package `.env.example` files show what each side actually reads.
