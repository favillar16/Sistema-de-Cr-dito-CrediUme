# Skill: Domain --- CAS

## Purpose

Protect the business domain from UI, transport and persistence concerns.

## Core entities

Client, User, Loan, Installment, Payment, Document, Audit Entry, and —
since `BR-CAJA-001..005` — Cash Session and Cash Movement.

Loans do not have a separate Guarantor entity: `BR-LOAN-005` implements
the guarantee as flat, nullable columns on `Loan`
(`guarantee_type`/`guarantee_amount`, one guarantee per loan), not a
child table.

**Cash handling exists again** (`specs/cash/README`). It had been
dropped, and an earlier version of this file said so; the
establishment reincorporated a teller position, so:

-   `CashSession` is a cashier's shift: opened with a declared cash
    amount, closed with an arqueo (expected vs counted vs difference).
    One open session per cashier, enforced by a partial unique index on
    the `OPEN` rows — not by a check in the servicer.
-   `CashMovement` is an entry or exit of cash within a session. Those
    generated by a cash loan payment carry `loan_payment_id`; the ones
    a cashier enters by hand do not.
-   `LoanPayment.payment_method` is `EFECTIVO` or `TRANSFERENCIA`
    (NULL reads as `TRANSFERENCIA` — every payment predating the
    module was one). `TRANSFERENCIA` still requires a non-empty
    `transfer_reference`; `EFECTIVO` instead requires an open cash
    session and posts a movement into it.
-   The expected amount of an arqueo is always recomputed server-side
    from the opening balance and the session's movements. Never accept
    it from the client — a close where the client supplies both the
    expected and the counted figure proves nothing.

## Rules

-   Business invariants belong in the domain/application layer.
-   Domain operations must be deterministic and testable.
-   Money must use `Decimal`, never binary floating-point arithmetic.
-   State transitions must be explicit and validated.
-   Invalid transitions must fail with meaningful domain errors.
-   Domain code must not depend on PySide6.
-   Domain code should not depend on gRPC generated classes.

## Typical state transitions

Loan (`LoanStatusEnum`): PENDING → APPROVED → ACTIVE → PAID

Alternative terminal states: DEFAULTED, EXPIRED (an undisbursed
APPROVED loan expires after 30 days, `BR-LOAN-003`, checked lazily on
read/write rather than via a scheduler).

There is no DRAFT state, and no REJECTED/CANCELLED/REFINANCED terminal
states in the current implementation.

## Forbidden

-   SQL queries inside domain objects.
-   UI calls from domain code.
-   Silent correction of invalid financial data.
-   Implicit state transitions.
